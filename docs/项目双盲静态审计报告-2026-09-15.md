# Kiro BYOK 项目双盲静态审计报告

日期：2026-09-15
范围：整个项目（排除本轮已结束的 `pelican-bicycle.html`）。
结论等级：P1=应在投产前处理；P2=重要缺口/应纳入下一迭代；P0=未发现有足够证据支持的阻断级问题。

## 方法与限制

本次采用主审 + 两路独立分工初审：A 审计计费、配额、OAuth、卡平台和账务持久化；B 审计补丁引擎、桌面端、管理端、部署和 CI；主审审计 provider、流式、会话、翻译、wire 与运维，并对候选项交叉核对。全程只读静态审查，未运行测试、构建、应用、Docker、脚本或网络请求；未读取实际凭证和数据库内容，也没有 `.git` 元数据可供历史变更核查。因此以下是源码证据审计，不是运行时复现或安全渗透结论。

## P1：投产前处理

1. **流式请求默认 60 秒总超时，健康输出也会被截断。** `crates/gateway/src/main.rs:245-250` 与 `provider/governance.rs:290-295` 将 provider timeout 设为 60 秒，`provider/openai.rs:256-262` 和 Anthropic 同样把它传给 reqwest 的请求总 timeout；而 `watchdog.rs:37-43` 的 hard timeout 是 600 秒。长上下文或慢生成超过 60 秒会在持续有 chunk 时失败。应拆分连接/TTFB/idle/总时长，并统一配置来源。

2. **客户端断开时，detached 上游读取任务可能继续占用连接和计算。** `crates/gateway/src/provider/mod.rs:296-302` spawn 独立 pump，等待 `stream.next()` 时没有与 `tx.closed()` 做 `select!`；仅在后续发送时才发现接收端消失。`stream.rs:178-201` 的外层取消不能直接终止该任务。应绑定 task 生命周期，或在读取等待中监听 channel closed 并 abort 上游。

3. **部分下游发送失败路径绕过结算。** `crates/gateway/src/stream.rs:88-92` 的 `BillingSettler::Drop` 会释放 reservation；但 `stream.rs:206-208、228-239、284-304` 多处 `send(...).await.is_err()` 直接 `break`，没有走 `tx.closed()` 分支的结算逻辑。在队列背压/断开竞态下，已经观察到的输出可能被释放而非入账。应统一所有退出路径的 finalization，并增加队列满时的断开用例。

4. **工具调用、推理调用和部分 cache-only 用量可能不计费或少计费。** `stream.rs:221-223` 只累计 Text 字符；`resolve_settlement_tokens`（`456-486`）只用 uncached/output 判定是否有 provider usage。没有 usage 的 tool-only 完成会返回 `None` 并释放 reservation；Anthropic 仅先报告 prompt usage 时，后续已经输出的文本也不会走估算分支。应维护统一的 reasoning/tool/text/cache 用量累加器，并区分“字段缺失”和“合法为零”。

5. **预留输出上限固定 4096，但实际请求可到 32000，结算失败会退回全部预留。** `conversation.rs:379-386` 固定预留 4096；`632-640` 与 `972-987` 之后按模型配置发送最多 32000。`billing/engine.rs:1492-1499` 余额不足时结算返回 `SettlementExceedsBalance`，`stream.rs:328-353` 随后 Drop 释放 reservation；因此低余额请求可能已消费较大输出却未形成账单。应在预留前解析最终模型/预算，或采用可持久化的超额结算/欠费状态，不能失败即全额释放。

6. **常见带版本路径的 provider 导入会拼出重复 `/v1`。** `provider/import.rs:163-164、248-249、318-320` 只去末尾 `/`；`provider/openai.rs:18-19` 无条件拼 `/v1/chat/completions`，Anthropic 拼 `/v1/messages`。现有导入 fixture 明确接受 `https://api.openai.com/v1`、DeepSeek `/v1/`、Siliconflow `/v1` 和 Groq `/openai/v1`，但测试未走真实 request URL。应集中定义 base URL 规范，兼容已含版本/前缀的地址，并补 import→request 集成断言。

7. **OAuth 激活忽略卡片模板有效期，统一使用 30 天。** `facade/oauth.rs:68-74、263-268` 将固定 `default_duration_secs` 传给 `activate_card_with_device`；`billing/engine.rs:981-987` 直接使用传入值，而 `card.rs:110-123` 已将模板期限保存到卡片。日卡、周卡、永久卡都会被错误延长或缩短。激活应优先使用卡片持久化的 `activation_duration_secs`，旧卡才使用兼容默认值。

8. **日/月额度只统计已入账 Usage，不统计在途 reservation；结算扩额也只检查余额。** `billing/engine.rs:1277-1287、1291-1327` 允许多个 Held 并以 ledger 计算窗口额度，`1492-1504` 扩额只检查可用余额。并发请求可以共同越过日/月上限，单笔超估算也可绕过额度。应在同一状态事务内检查“已用 + 在途 + 本次新增”，结算扩额复用同一规则。

9. **账务提交点后的目标文件 I/O 失败会造成接口结果与重启结果不一致。** `billing/engine.rs:555-570` 已写 generation 和 anchor 后，更新主文件仍可能失败并返回错误；`commit_candidate_snapshot:589-607` 因而不发布内存候选，但启动加载会按 anchor/generation 恢复新状态（`647-686`）。调用方可能按失败重试，重启后却看到已提交账务。应明确 anchor 为提交点，提交后错误进入可修复状态而不是返回“未提交”。

10. **显式快照同步可能以旧快照覆盖已提交的新事务。** `billing/engine.rs:479-486` 在持久化锁外导出快照，`489-497` 之后才加锁，`admin.rs:1375-1414` 暴露同步入口；没有过期序号拒绝。同步 A 可先读旧状态，事务 B 成功持久化后，A 再覆盖 B。应在一致的锁顺序下完成读取、序号分配和发布，或按序列号拒绝陈旧快照。

11. **发卡订单幂等记录只在内存中，重启/淘汰后可重复发卡。** `billing/card_platform.rs:174-185` 只查 `order_cache`，生成并持久化卡片在 `209-225`，结果到 `233-249` 才写缓存。服务重启、TTL 到期或缓存淘汰后，重复订单会生成新卡。应把 order_id、请求指纹和可重放结果与卡片创建放在同一持久化事务中。

12. **补丁替换可能把带引号的 JavaScript 表达式嵌入字符串内部。** `patch-engine/src/patch.rs:237-247` 对 needle 做纯文本替换，默认 replacement 在 `241-243` 含双引号；现有 `takeover_test.rs:126-129` 的 needle 位于双引号字符串中。结果可能是无效 JS，或仍只是字符串文本；但 `apply` 仍写标记并返回成功。应匹配完整 AST/字符串表达式，限定替换次数，并做补丁后语法/端点求值验证。

13. **二次接管会覆盖首次原始快照。** `patch-engine/src/snapshot.rs:142-197` 每次 takeover 都重新规划并保存 snapshot；虽 `patch.rs:203-205` 对扩展已打补丁幂等，但设置快照仍可能被当前 BYOK 状态覆盖。再次 activate 后 restore 不能回到最初官方设置。应保留首次快照，或将重复接管明确设计为配置更新而不是新 rollback 基线。

14. **IDE 升级后恢复流程可能把旧扩展写回新安装目录。** `patch.rs:145` 可报告 `UpgradeDetected`，但 `restore:270-282` 不校验版本/哈希，直接写旧 backup；现有 `takeover_test.rs:151-167` 还把恢复旧版作为期望。应将备份绑定版本和文件哈希，发现升级时拒绝跨版本覆盖并重新建立基线。

15. **桌面激活链路没有卡密登录，却显示“硬件指纹绑定成功”。** `apps/desktop-ui/index.html:876-888` 只提交固定 `gateway_url`；`run_desktop.py:191-200` 只调用 `patch-cli activate`；`patch_cli.rs` 的激活路径只做本地接管。卡密为空、Kiro 未安装或网关不可用时，仍可能只完成本地修改并展示成功；默认端口 `44040` 也与 Compose 网关 `19820` 不一致。应先验证安装，再完成卡密登录/绑定/token 保存，所有步骤成功后才能提示激活。

16. **默认 JSONC 清理会修改用户字符串内容。** `patch-engine/src/settings.rs:315-364` 虽处理了字符串状态，但最后对整个文本执行 `replace(",}", "}").replace(",]", "]")`；合法设置值含这些字符时会被持久化改变，而 `settings.rs:133` 只备份托管键。应仅在字符串外移除尾随逗号并补保真用例。

17. **恢复脚本的“在线检测”与默认 Compose 网络不匹配。** `deploy/backup/restore.sh:30-54` 探测宿主机 `127.0.0.1:19820`，而 `docker-compose.yml:41-46` 只 `expose` 容器内部端口。宿主机探测失败会被当作停机，随后 `restore.sh:224-229` 覆盖共享数据；运行中网关的内存状态可能再次刷回。应使用 Compose 状态/容器内 healthcheck 做可靠判定，未知状态拒绝恢复。

18. **恢复脚本没有真实网关验证器时以结构检查放行。** `restore.sh:131-168` 在找不到 binary/cargo 时使用 Python，仅核对 checksum、JSON 对象和 anchor；这不能验证 AEAD KEK、版本、账本不变量或生产加载能力。应在部署镜像内运行同版本 `verify-snapshot`，无法验证时终止。

## P2：重要不足

19. **真实流式路径未使用已实现的 stop reason 映射。** `translate/from_provider.rs:37-45` 把 `stop/tool_calls/length` 映射成 Kiro 的 `end_turn/tool_use/max_tokens`，但生产 `stream.rs:300-304` 直接发送 provider 原值；该映射函数目前仅在 `tests/translate_test.rs` 被调用。结果是测试通过的协议语义与真实流不一致。应让生产路径复用同一 translator，并覆盖 OpenAI/Anthropic 真实事件链。

20. **contextUsage 使用拆分 usage 事件的当前值，且忽略管理端配置的 context window。** `stream.rs:269-298` 虽为结算累计最大值，但上下文百分比使用当前事件；Anthropic 的 `message_delta` 可能把 prompt 置零，导致 UI 从真实高占用跳到低占用。`conversation.rs:825-826` 用内置模型库解析窗口，而 virtualization 可广告管理端配置窗口。应以累计 usage 和最终有效窗口生成上下文事件。

21. **环境变量单 provider 模式会展示虚拟模型，却静默使用同一个 UPSTREAM_MODEL。** `gateway/main.rs:221-256` 配置 provider 未同步填充 model map；`virtualization.rs:40-87` 仍返回 dummy 菜单，`conversation.rs:547-568` 在空 map 时放行任意请求，vision 支持也只从 model map 设置。用户选择的模型/视觉能力与实际请求不一致。应在 env-only 模式明确只展示实际模型，或建立完整映射并拒绝不支持的输入。

22. **桌面解绑不清凭据，且失败分支仍显示解绑完成。** `index.html:931-942` 只调用 `/api/restore`，异常时仍切换未激活页面；snapshot restore 只处理设置、扩展和快照，不处理 token/远端绑定。应实现明确的凭据清理/远端解绑，并在每一步确认成功后更新 UI。

23. **批处理启动器打开静态 HTTP 页面，未启动所需桥接服务或 session token。** `启动桌面客户端.bat:10-30` 只启动 `python -m http.server` 并打开无 token URL，而页面的 `apiCall` 要求 `X-Kiro-Session-Token`（`index.html:728-740`）。双击启动器可见页面但激活、恢复、诊断等 API 操作不可用。应统一委托 `run_desktop.py` 并传入会话。

24. **管理 UI 丢弃批量制卡的 rawCode，导出按钮是占位。** 后端 `facade/admin.rs:824-839` 返回 `rawCode`，但 `apps/admin-ui/src/App.tsx:154-162` 只提示数量并刷新，`428-431` 的 CSV 导出只显示“当前已禁用”。运营流程无法从界面交付新卡密。应提供一次性内存结果页、复制/下载和离开即不可恢复的提示。

25. **指标在 HTTP 响应头返回后就结束计时，且账务指标没有生产调用者。** `ops/metrics.rs:127-136` 在 `next.run` 返回 response 后即 `end_request`；流式 body 的错误和持续时长不在请求生命周期内。`record_request_success`（`47-52`）仅定义/测试使用，生产结算成功不会更新 credits counter。应在 body/stream 完成时记录，并把结算事件接入指标。

26. **账本归档删除在线记录后，幂等、额度和恢复校验仍依赖在线账本。** `billing/engine.rs:3089` 移除旧 ledger 条目，但调账判重在 `2544`、恢复/额度累计在 `3157` 等路径仍查在线集合。归档后重放可能重复调账，窗口额度漏算，完整性校验可能误拒绝。应保留不可删除的幂等索引、累计摘要和窗口用量。

## 测试与工程缺口

- CI（`.github/workflows/ci.yml`）仅覆盖 Ubuntu Rust、前端安装/构建及静态扫描；没有 Windows 启动器、真实浏览器、Compose/备份恢复、容器内验证和流式断连场景。
- 补丁测试检查 marker/文本，不检查 JavaScript 可执行性；没有二次接管快照、JSONC 字符串保真、升级后恢复基线的正确契约测试。
- 账务测试没有覆盖在途额度、结算扩额失败后的收费语义、提交点后 I/O 故障、显式同步与交易并发、重启后的订单幂等。
- 流式测试未覆盖真实 reqwest pump 在接收端消失时的取消、背压 send error、tool/reasoning-only usage、Anthropic 分拆 usage，以及生产 translator 的 stop reason。
- 管理/桌面测试未覆盖“卡密生成到 UI 交付”、激活/解绑端到端、session token、端口配置、失败提示和凭据清理。

## 已确认的正向控制

未发现足够证据支持 P0；也不应把下列现有控制重复列为缺陷：生产默认要求关键 secret，快照默认需要 master KEK 并在加载失败时拒绝，默认监听 loopback，管理/公开路由有分区，portal 有挑战/限速，body/wire 有大小上限和 CRC/边界检查。以上控制仍需在 CI/部署演练中验证，不能替代本报告列出的链路缺口。

## 建议顺序

第一批先处理流式取消与结算一致性（2-5）、账务预留/额度/快照发布（7-11），以及 provider URL、补丁和恢复脚本（6、12-18）；第二批闭合桌面激活/解绑、制卡交付和真实 translator（15、19、22-24）；第三批补齐模型虚拟化、context、指标和归档摘要（20-21、25-26）。在这些静态问题被修复并由 Linux、Windows、容器恢复演练和真实流式集成测试覆盖前，不建议把项目标记为“已完成整改/可直接投产”。
