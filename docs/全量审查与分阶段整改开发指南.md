## 4. 给执行模型的硬规则

1. 每次只做一个任务；先读指定文件、所有调用方及相关测试，再修改。不要把本文风险直接改成任意实现。
2. 先加能暴露问题的最小失败测试，再修代码，记录修前失败和修后成功。同一资金/身份共享路径必须覆盖其他调用方。
3. 所有测试使用临时数据目录、假密钥和本地 mock 上游；不得使用真实卡余额、真实令牌或生产备份。
4. 不删除现有测试，不通过修改期望值掩盖协议/资金错误，不以忽略错误、禁用加密、放宽认证修复失败。
5. 当前不是 Git 仓库。开始前列出涉及文件并保留原件或文件哈希；不得清理工作区未知文件，不自动初始化/重置仓库。
6. 每项产出：修改文件清单、失败输入、根因、变更说明、准确命令与退出码、脱敏证据、未解决项。不能只写“已实现”“已接入”。
7. 本文没有规定的新架构不要自行引入。保持单机运行；Postgres、分布式队列、微服务和新桌面框架均不是本轮默认要求。
8. 操作涉及 API/存储兼容性时先列出现有消费者和迁移策略。若关键规格无法确定，标明阻塞，不制造一个测试自证的业务规则。

T01 → T02 → T03。之后 T04 → T05；T06 可在基础构建通过后实施。T07 依赖 T02/T03；T08 依赖 T06 与 T07；T09 依赖 T04；T10 最后收口。这里的并行可能性不授权启动子代理。

### T01：恢复可复现构建

范围：provider_import.rs、实际需要变更的前端依赖文件、CI 和环境说明。禁止顺手升级整个依赖树。

步骤：
1. 阅读 provider_import.rs 的响应 helper 导入及错误分支；补足现有 error_response 导入，不复制一份 helper。
2. 用 cargo check --workspace --all-targets --locked 确认编译，并继续修复实际暴露的错误，不能假定只缺一个导入。
3. Windows 使用 Visual Studio Developer shell/MSVC Build Tools，确认 where.exe link.exe 首项为 MSVC；不要删除 Git 自带工具。无法提供环境时在可用 Linux 环境执行测试并记录平台限制。
4. 保留锁文件，在干净临时副本执行 npm ci、npm ls vite --depth=0、npm run build。先验证声明和 lock 一致性，再决定是否需要修改 lock；不要用已有 node_modules 代替复现。
5. Rust CI 命令增加 --locked；保留现有前端 npm ci。不要添加无关框架。

验收：cargo check/test 全部退出 0，npm ci/build 退出 0，npm ls 无 invalid。Windows 与 Linux 的结果分开记录。任何环境阻断仍记阻断，不打勾。

### T02：资金与身份变更的事务边界

范围：billing/engine.rs、相关 facade 错误映射及测试。先枚举 sync_to_disk、sync_to_disk_checked 和 save_to_file 全部调用方。

失败用例：临时路径故障导致调账持久化失败后读取余额与流水，再修复存储并重试相同业务请求；当前实现存在第一次失败但余额已变的路径。Windows 权限测试不可靠时使用测试专用故障注入，不依赖真实磁盘填满。

步骤：
1. 定义状态：未提交、已提交、结果未知。只有确实未提交才可自动重试；不能把“返回 I/O 错误”直接等同“没有发生”。
2. 在统一串行变更边界完成候选状态计算、持久提交、可见状态发布；与 T03 的磁盘提交点保持一致。优先复用现有锁与快照，不为每个 API 增加不同回滚方案。
3. 禁止简单在保存失败后恢复全局旧快照：并发请求可能已完成更新，这会覆盖其他人的成功操作。
4. 覆盖 reserve、settle、release、janitor、调账、批量制卡、卡撤销、provider/key 和价格变更。逐个决定哪些是必须持久提交的操作；移除这些路径的只打印错误行为。
5. 调账与其他可重复资金动作增加持久幂等键；相同键同参数返回同结果，不同参数冲突。失败重试、响应丢失重试、重启重试均不能重复入账。
6. 持久化故障时 readiness 和请求准入策略一致；阻止继续接收依赖不可靠资金状态的新计费请求。明确已经开始的流如何结束和对账。

验收：每个故障点下余额、预留、流水和重启后的状态一致；并发成功请求不被失败请求回滚；已确认成功的交易重启后存在且仅一次。未知提交必须可通过幂等键查询，不能盲目重复执行。

### T03：快照发布、崩溃恢复与增长上限

范围：engine.rs 快照保存/加载及临时目录集成测试。已有 AEAD 和 anchor 必须保留其安全属性。

步骤：
1. 明确提交点。最小可行方案是完整 generation 文件与校验元数据准备好后，用一个当前版本指针发布，保留上一可恢复版本；也可提出更简单且通过同样故障矩阵的方案。
2. 注入故障：临时写入、sync、快照替换、anchor 替换、目录同步及内存元数据更新前后。每点重启读取，结果只能为完整旧版或完整新版。
3. 已发布快照但后续步骤失败属于提交不确定性，配合 T02 恢复；不要删除 anchor 或自动接受不匹配以“恢复成功”。
4. 核验 AEAD 密钥错误、截断、checksum 不匹配、版本不支持、缺 anchor 的既有兼容策略；遗留迁移必须显式授权。
5. 说明本地快照和本地 anchor 一同被旧版本替换时的威胁边界。仅有本地配对不能证明抵抗整个目录回滚；不要宣传外部不可回滚保证。
6. 当前加载上限 MAX_SNAPSHOT_BYTES 为 256 MiB。测量持续流水增长和全量保存延迟；达到加载上限前应阻止生成不可重载文件并提供可验证归档方案，不允许静默丢账。是否需要数据库以测量为依据。

验收：故障矩阵每点可恢复、无混代文件被接受；旧快照迁移明确；正常重启保留幂等信息；容量边界不产生“能写不能读”的已确认状态。

### T04：Provider 从导入到真实请求的生产闭环

范围：main.rs、facade/mod.rs、provider_import.rs、conversation.rs、provider/runtime.rs、governance.rs。

失败用例：通过实际生产路由创建管理员 session、导入本地 mock Provider，然后发起对话；记录到底命中导入地址还是环境默认地址。不要仅测试手工 with_runtime 构造的 handler。

步骤：
1. 启动只创建一个共享 ProviderRuntimeRegistry，加载已持久化的 provider/key，并同时传入导入和对话入口。密钥按已有安全存储方式使用，不进入日志。
2. 明确环境上游和管理端配置的优先级。当前 main 在无 UPSTREAM_API_KEY 时默认拒绝启动；改为有可用持久配置即可启动，还是继续要求 bootstrap，必须写清并测试，不能暗中开启 stub。
3. 明确禁用、更新、删 key 后运行池如何更新，重建 pool 是否清空健康状态；旧请求与新请求的配置边界要一致。
4. 检查 conversation.rs:643 的 default_pool 和 self.pool 优先级。显式指定但不存在/禁用的 provider 不应静默改走任意池，除非明确配置了 fallback。
5. 跨 provider/model fallback 必须重新校验协议、视觉能力、模型映射、价格和额度。明确对外收费按请求模型还是实际模型，记录实际上游成本；不能自行改变合同价格。

验收：导入后无需重启命中目标；重启后仍命中；无权限导入失败；禁用立即影响新请求；两种 provider 的跨协议 fallback 可用；无法路由返回明确错误且释放/结算仅一次。证据包括 mock 服务器收到的模型和路径，不含 key。

### T05：无损协议翻译与计量归一化

范围：kiro-wire 请求类型、provider/mod.rs、translate/to_provider.rs、tools.rs、openai.rs、anthropic.rs、stream.rs 和现有测试。

步骤：
1. 用脱敏真实格式 fixture 建立“历史 assistant 工具调用 → 历史 user 工具结果 → 下一轮输入”，包含两个并发工具、嵌套 JSON 参数、失败工具、长中文名称和图片。
2. 中间消息保留工具 ID、名称、参数、结果状态及内容；不要只保存 ID。恢复历史 user context 的工具结果，工具名缩短映射须适用于当前声明及历史。
3. OpenAI 编码 assistant.tool_calls、tool_call_id、function 工具定义；Anthropic 编码 tool_use、tool_result、input_schema 和 image/source。不要透传 Kiro toolSpecification 或 OpenAI image_url 给不兼容上游。
4. 孤儿修复以时间顺序和调用配对为准，不能因为未来存在同 ID 就认为此前结果合法；不可凭空生成成功工具结果。
5. 明确统一 usage 口径。建议使用互不重叠的 uncached input、cache read、cache write、output；若保留 prompt_tokens，须定义为是否含缓存，并在适配器一次性归一化。
6. 关键 fixture：Anthropic input=100、cache_read=200、cache_creation=50、output=20，应计非缓存输入 100，总输入 350；OpenAI prompt=350、cached=200，应计非缓存输入 150。以上以对应官方协议和脱敏响应核实后固化。
7. message_start 与 message_delta 的 usage 是部分字段或累计值，不可重复相加；字段缺失不能抹掉先前值。累计快照使用 max 的前提也必须由协议确认。
8. 检查图像验证是否在实际解码前生效；覆盖无效 base64、伪 MIME、超大尺寸、解码分配上限、历史图片。不要仅测试限制常量存在。

验收：校验最终发送 HTTP JSON，不仅中间结构；两种 mock 上游严格拒绝非法 schema；工具往返 ID/参数不丢；计费 fixture 输出精确且不溢出；真实上游兼容性另记环境门禁。

### T06：流式异常与幂等结算

范围：stream.rs、conversation.rs、watchdog、idempotency 及 billing。

本项是故障验证任务，不能在测试前断言所有断流都免费或重复收费。BillingSettler 析构会释放预留，但已有其他错误结算路径，须以真实分支区分。

步骤：
1. 本地 mock 依次产生：连接失败、首 token 前超时、部分文本后 EOF、usage 前断流、usage 后断流、明确 Done、重复 Done、非法 SSE、取消请求、进程重启。
2. 为每种情况定义客户收费与上游成本规则，尤其“已消费但无 usage”的估算/待对账策略；不得默认用零成本掩盖损失。
3. 断言预留最终状态、余额、ledger 次数、容量 permit 释放、上游取消和幂等缓存终态；错误事件不得被缓存为完整成功。
4. 同一 invocation 并发重试和中断重试只能产生一次业务结算。结合 T02 验证结算 I/O 失败。
5. 验证 HTTP timeout 是否覆盖响应 body 流，不能用中间件名称证明慢流受到限制。

验收：上述矩阵均有可运行检查；无永久 Held、无负余额/重复流水、无容量泄漏；取消后 mock 可观察连接终止。缺 usage 的业务决定必须写入测试说明。

步骤：
1. 删除或明确禁用定时器模拟成功状态；激活、恢复、窗口操作必须来自实际执行结果。未接入项不得显示“成功”。
2. 先做最小真实入口调用 patch-engine 的现有流程，再绑定 UI；不要先重写整套桌面框架。浏览器静态页本身不能直接证明 Rust 文件操作发生。
3. 修复启动器服务生命周期：明确谁持有服务、何时关闭；Chrome 已运行时新进程可能立即退出，不能只 wait 浏览器子进程。占用端口时验证服务身份，不直接信任任意本地进程。
4. 本地桥接仅 loopback，使用随机会话凭据、Origin 校验和明确操作授权，不提供任意路径写入/任意命令接口；网关 URL 不成为代码注入内容。
5. 进程探测使用 Running/Stopped/Unknown 语义；Unknown 禁止改 Kiro 文件。覆盖命令不存在、非零退出、权限不足及进程状态改变。
6. 单实例锁处理同进程多 guard、跨进程竞争、陈旧锁和 PID 复用；优先使用可靠 OS 锁，若保留文件锁须证明所有权后才能删除。
7. 设置合并、扩展补丁、token 写入和恢复作为可恢复流程：保存原始文件、验证版本/哈希、原子写、错误回滚。用户随后修改的文件不能被旧备份无条件覆盖。
8. token 文件权限与日志脱敏做回归；当前 Debug 已脱敏，不重复“修复”已不存在的问题。

验收：临时假 Kiro 目录完成激活/恢复哈希检查；两进程竞争仅一方成功；探测失败零写入；启动器退出/窗口关闭行为符合约定。最后在明确授权的真实 Kiro 版本完成截图、请求证据、恢复证据；缺真实环境时本项不得全部通过。

### T09：管理端从按钮到后端状态

范围：App.tsx、api.ts、对应 admin/provider API。

步骤：
1. 建立按钮清单：已接入、未接入、明确不支持。优先修复“新建分组”“添加 Provider”纯 toast；没有后端能力时禁用并准确表达状态，不伪造向导。
2. 每个操作验证请求、服务端状态和刷新后读回；错误不显示成功，重复提交受控，空/加载/过期/权限不足状态完整。
3. 后端已有 session/revoke 且语义为撤销所有 session。不要直接当作单设备 logout 使用；选择新增当前 session 撤销或明确“全部退出”，本地 clearSession 与服务端语义配套。
4. 会话过期重新认证，退出后旧 token 按选定语义失效；不得将 bootstrap 管理密钥存 localStorage。
5. 浏览器检查桌面/窄屏布局、键盘操作、焦点、输入错误、表格溢出；不要为了补功能重做全站样式。

验收：真实页面操作有网络请求和刷新后状态证据；401/403/500 显示正确；不泄露原始秘密；所有可点击成功操作都可观察到真实效果。

### T10：部署、权限与最终门禁

范围：deploy、CI、回归报告；不在本机缺 Docker 时伪报容器成功。

步骤：
1. 在具备 Docker 的干净环境构建并启动 Compose，验证 non-root 对 bind mount 数据目录的实际写权限；保持 REQUIRE_ENCRYPTED_SNAPSHOTS=true。
2. 检查 Caddy /admin 与 /api/v1/admin 的实际匹配、网关认证、TLS、流式反代，确认外部不能直连绕过预期边界；Basic Auth 不代替应用授权。
3. 可信代理网段匹配实际网络，测试非可信来源伪造 X-Forwarded-For 无效；不要只凭默认 172.16.0.0/12 判定可信部署。
4. HOST 非法、secret 文件不可读、账本损坏、KEK 错误、上游不可用分别验证启动/健康响应，不允许静默切换演示模式。
5. 固定可复现工具链和镜像版本策略；保留现有安全扫描。实际运行依赖扫描并记录结果，不能推测无漏洞。
6. 在隔离部署完成制卡、认证、对话、工具往返、撤销、重启、备份恢复和管理端操作。日志必须可追踪 request/invocation，同时不含凭据。

验收：冷启动与重启通过；资金持久性、鉴权、流式和恢复检查通过；容器停止后无丢失已确认交易；产出脱敏发布检查记录。
