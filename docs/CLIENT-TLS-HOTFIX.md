# 客户端 TLS 与启动挂起修复

修复范围：Kiro 1.1.14 当前安装包中的代理库兼容问题，以及 Windows 子进程输出管道继承。

## 根因及变更

- 内置 https-proxy-agent 对 IP 地址不设置 SNI，同时删除 TLS options.host；Node 在隧道上按 localhost 校验证书，引发 ERR_TLS_CERT_ALTNAME_INVALID。补丁仅保留目标 host，保留系统证书链与主机名校验，不添加任意证书信任。
- Kiro 子进程继承 patch-cli 被 Python 捕获的输出管道，导致 CLI 已退出但界面仍等待读取结束。启动时使用空标准流，并在 Windows 清除原标准句柄的继承标志。回归中仅重定向标准流仍失败，清除句柄继承后通过。
- 已接管的扩展在下次安全接管/启动时进行兼容升级，先校验现有内容哈希，保留原始备份；运行中的 IDE 不修改。
- 已有有效本地凭据及接管快照时，重新打开客户端默认进入状态页，无需重复输入卡密。

## 验证

- patch-engine 库测试 14 项通过，包括真实子进程输出管道回归。
- 桌面桥接及浏览器回归 11 项通过，包括重新打开后的状态页恢复。
- patch-engine all-targets Clippy -D warnings 通过；Debug patch-cli 已重新编译。
- test_proxy_tls.cjs：通过本机代理复现原证书错误，保留 IP host 后 HTTPS 200，错误主机名仍拒绝，直连 Node HTTPS 200。
- 实际安装扩展与已有哈希一致；兼容补丁命中一次；完整修复候选通过 node --check。
- 使用本机已有登录凭据仅查询额度和模型接口，均 200；当前返回唯一模型 claude-sonnet-4-6。未进行推理、充值、解绑或重新激活。

## 待应用

当前运行中的 Kiro 未被关闭，也未改写其扩展。用户保存工作并完全关闭 Kiro，再重新打开 Debug 客户端，通过“偏好设置 → 刷新状态 / 查看详情 → 启动 Kiro”应用兼容补丁。此步骤复用既有授权，不需要卡密。实际 IDE 账号和模型列表的恢复仍需启动后确认，不将独立 Node 测试等同于真实 IDE 验收。

无需重部署云端；此次是本地客户端修复。兼容替换针对已验证的当前扩展构建，未来 Kiro 升级仍须重新验证。
