- **修前失败输入与命令**：
  - 原 `persist_snapshot_to_file` 先将内容 rename 为目标快照 `path`，再原子写 `.anchor`。若进程在 rename `path` 后、写 `.anchor` 前崩溃，重启时 `path` 具有新校验和但 `.anchor` 仍保留旧序列号/校验和，`load_from_file` 报“anchor mismatch or rollback detected”从而无法启动，且缺失基于分代文件的自愈机制。
  - 原 `persist_snapshot_to_file` 未校验 `file_content.len() > MAX_SNAPSHOT_BYTES`，当状态数据膨胀超过 256 MiB 时仍能成功写入，但重启后 `load_from_file` 强制拒绝加载，造成“能写不能读”的致命不可逆停机状态。

  - F05: 提交点次序与崩溃恢复模型倒置。快照文件与锚点指针应当以“锚点指针原子发布”为单一提交点；未更新锚点前任何文件不得视为已提交；更新锚点后若目标主文件更新被中断，必须能根据锚点引用的分代文件完成幂等自愈。
  - 容量硬上限缺失防写门禁：加载侧限制了 256 MiB，但写入侧未对称限制，违反“写入前置校验”原则。
  - 缺乏流水生命周期管理接口，账本历史数据无限堆积在活跃快照中。
- **最小变更**：
  1. 架构统一确立**单一原子提交点**（Generation + Anchor 指针模型）：
     - 步骤一：写分代文件 `path.gen_<sequence>` 并调用 `sync_all()` 强制刷盘。
     - 步骤二（**提交点**）：原子更新 `.anchor` 文件，写入 `{ version, sequence, checksum, generation_file: Some(gen_file_name) }`。此操作落盘即代表本代数据正式提交生效。
     - 步骤三：原子更新主目标快照文件 `path`，并执行父目录 `fsync`。
     - 步骤四：清理历史分代文件，始终保留当前代与上一可恢复代（`seq >= sequence - 1`）。
  2. 崩溃自愈加载（`load_from_file`）：
     - 读取 `.anchor` 并校验单调序列号；
     - 若主文件 `path` 校验和匹配锚点，直接加载；
     - 若主文件 `path` 不存在或校验和不匹配（在步骤二与步骤三之间发生崩溃或断电中断），检查锚点指定的 `generation_file`；若分代文件校验和匹配锚点，则从分代文件加载，并执行自愈写回主文件 `path`，使后续加载恢复正常；
     - 若锚点与主文件、分代文件均不匹配或损坏，严格 fail-closed，拒绝启动，不自动删除锚点。
  3. 双向硬上限门禁：

### T06：流式异常与幂等结算

- **任务编号与阶段名称**：T06：流式异常与幂等结算
- **复现方式及原始失败**：
  1. **首 token 前超时与连接失败**：当上游连接失败或在首 token 前触发超时，若预留未能及时释放，预留额度永久挂起（Held），造成可用额度被永久冻结。
  2. **部分文本输出后异常断流（已消费但无 usage）**：上游在发送部分响应文本后突然 EOF 或断开连接，此时上游尚未发出 `Usage` 块。原始代码要么在 Drop 中全额释放预留（导致客户免费消费昂贵的大模型算力，平台蒙受直接财务损失），要么抛错导致预留悬空。
  3. **客户端中途主动断开（Cancel / Disconnect）**：客户端在收到部分 token 后关闭连接，若网关任务未感知下游通道关闭，将继续向上游拉取计费流导致算力泄漏；且未按已实际交付给客户端的内容进行结算。
  4. **并发与重复 Done 事件**：同一个 invocation ID 重复触发 Done 事件或并发请求，若未做原子消费保护，会导致多扣费或重复流水生成（double-billing）。
  5. **幂等状态机失真**：发生异常终止的 invocation 若未将幂等状态标记为 `failed`，重试请求可能复用半生半死的状态或再次执行扣费。
- **根因及调用链**：
  - **F09: 流式生命周期断流、超时与幂等结算漏洞**：
    - `crates/gateway/src/stream.rs`：`BillingSettler` 依赖 Drop 机制释放预留，但对“已消费文本但无供应商 usage”场景缺乏业务保底结算策略；未跟踪向下游发送的实际文本字符数；
    - `crates/gateway/src/facade/conversation.rs`：构建 `BillingSettler` 时未传递估算输入 Token 数，导致流在异常断流时无法推导输入成本；
    - 下游断开（`tx.closed()`）、上游解析错误（`ProviderError::Parse`）和非正常 EOF 分支中，未将幂等守卫（`IdempotencyGuard`）显式标记为 `fail()`，导致幂等重试契约与账本结算脱节。
- **最小变更**：
  1. **保底结算策略与字符跟踪（`crates/gateway/src/stream.rs`）**：
     - 在 `BillingSettler` 中新增 `estimated_input_tokens: u64` 属性与 `with_estimated_input` 构造器；
     - 在 `create_stream_guard` 中引入 `emitted_output_chars: usize`，当下游通道成功接收到 `assistantResponseEvent` 文本时动态累加字符数；
     - 实现 `resolve_settlement_tokens` 结算策略：
       - 若收到上游真实 `Usage`，以真实值精确结算；
       - 若未收到真实 `Usage` 但 `emitted_output_chars > 0`，按 `(emitted_chars + 3) / 4`（至少 1）推算输出 Token，输入 Token 采用 `estimated_input_tokens`（至少 1）进行保底结算，杜绝白嫖；
       - 若未收到 `Usage` 且无任何文本产出，结算器安全 Drop，正常释放预留，客户端可零成本重试；
