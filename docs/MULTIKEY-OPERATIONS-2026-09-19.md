# 多 Key 与模型权限操作说明

## 发布流程

1. 管理后台「供应商」中添加渠道（协议、基础地址、密钥）。导入渠道不再自动发布用户模型。
2. 每个 Key 使用独立 Key ID，填写允许模型的精确上游 ID。空列表表示不允许调用任何模型；历史数据中的未配置权限暂时保持兼容。
3. 「获取模型草稿」使用该 Key 请求上游模型目录，只填入草稿，不保存权限、不修改模型映射。当前只取一页；上游返回 has_more 时必须补全核对。
4. 核实可调用性、上下文能力和采购价格后，保存 Key 权限。
5. 在模型映射与定价中显式发布到目标卡密分组。多个渠道的模型可统一映射到用户目录；同一公开模型可配置主渠道和候选回退渠道。不能把发现目录当成全部可调用、全部已定价的证明。

## 路由与记账

- 路由同时受用户分组、已发布映射、渠道状态、Key 启用状态、模型权限和 Key 健康状态约束。
- 同一渠道内按权重挑选具备目标模型权限的 Key；限流或临时失败进入冷却，鉴权失败标记不可用。
- 一次网关执行最多三次上游尝试，整体启动阶段有时间上限。仅在尚未向用户输出内容时重试，已经开始的流不会自动重放。
- 同一 invocation ID 会累计现存跟踪记录里的尝试次数；结算会合并失败与成功尝试。幂等扣费依然由账本与预留控制，不依赖跟踪数据。
- 跟踪不保存对话内容、上游响应正文或 API Key。后台展示的是 Key 标识，不是密钥。
- 部分内容已经交付后中断，可能按已用量计费，并将最终跟踪状态记为失败。

## 当前边界

- 真实多供应商、多 Key 切换须在取得第二把实际密钥后另行验收；现有不同 Key 能力匹配与故障切换使用模拟上游测试。
- 模型发现没有自动分页与定时全量同步；用户目录不会自动取所有上游目录的并集。
- Key 编辑尚无乐观版本冲突控制或独立配置审计流水，操作员应串行编辑并复核配置。
- 请求跟踪是尽力持久化的可观测数据；进程终止、外层超时取消或管理员清理跟踪可能导致跨请求尝试预算不完整，不能作为严格的持久限额。账本幂等仍独立生效。
- 新版跟踪包含 in_progress 状态。回滚旧版前须确认数据兼容；部署脚本仅在开放流量前的失败路径恢复停机备份，切勿在产生新订单或消费后直接覆盖账本。
- 本轮不修改商用采购价格、销售价格及利润配置；已有测试费率不能作为已核实的利润依据。
- 协议自动验收不等于真实 Kiro IDE 全部 GUI 交互验收。
