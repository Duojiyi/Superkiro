## B1 · P1：崩溃遗留的操作锁会永久阻断正常恢复

- 证据：`D:/Desktop/kiro byok/crates/patch-engine/src/snapshot.rs:177-188`、`:324-340` 使用 `create_new(true)` 创建空锁文件，只在 `Drop` 中删除，没有持有者身份或操作系统文件锁；`D:/Desktop/kiro byok/crates/patch-engine/src/desktop.rs:55-56` 使用同一机制建立 session-lock，`:280-286` 恢复前必须先取得该锁。普通额度读取也在 `:70-71` 取得 session-lock。
- 触发：读取额度、连接或恢复过程中宿主被结束、崩溃或机器重启，未执行 Drop；仅额度读取被中断也足以留下锁。
- 影响：重开客户端并不能恢复。后续额度/连接/恢复报锁冲突；若已有接管状态，用户还可能被退出前恢复要求卡住。保留备份是正确的，但现有客户端没有解除已死亡持有者锁的恢复入口。
- 最小方案：改为持有文件句柄的跨平台 OS 排他锁，文件可以保留而锁随进程退出释放；或保存持有者 PID 和启动身份，提供经核实无活跃持有者的显式解锁。不能无条件删除锁，也不能只按时间判断。

## B2 · P1：恢复只验证补丁文件，不验证原始备份内容

- 证据：`D:/Desktop/kiro byok/crates/patch-engine/src/patch.rs:250-255` 备份原始内容，但 state 仅记录 patched 内容的 hash；`:264-270` 对备份只检查 `is_file()`；`:301-307` 将备份任意字节写回扩展，随即删除备份和 state。
- 触发：接管成功后 `.kpatch-backup` 被截断、损坏或替换，而当前 extension.js 和 patched hash 保持不变。例如备份变成零字节普通文件。
- 影响：验证仍通过，恢复将空文件/错误版本/替换内容写入扩展并删除恢复证据；“恢复成功”并不证明恢复到接管前内容。不是声称已观察到恶意篡改，而是恢复真实性校验缺失。
- 最小方案：在写入前保存原始字节 hash、长度及必要版本信息，并在恢复前校验备份。校验失败保留所有恢复记录并拒绝覆盖；若需防御同权限主动篡改，普通 hash 文件本身不是认证机制，必须另设可信存储边界。

## B3 · P2：失败接管/恢复产生的残留备份会阻断后续所有接管

- 证据：`D:/Desktop/kiro byok/crates/patch-engine/src/patch.rs:245-256` 先创建备份，再写 state 和替换目标；`:155-170` 将“无补丁标记但有备份”统一判为 `UpgradeDetected`；`:294-295` 恢复对此直接返回 `Ok(false)`。`D:/Desktop/kiro byok/crates/patch-engine/src/snapshot.rs:303-310` 接受 false 并删除 snapshot；`:166-170` 下一次接管又要求 Official。`patch.rs:303-306` 写回成功、删除备份失败也进入同类状态。
- 触发：备份创建成功后 state 写入或目标替换失败，原文件仍是官方内容；用户随后执行还原。另一条触发路径是写回完成但备份删除失败后重试还原。无需进程崩溃即可触发。
- 影响：还原可以被宿主视为完成并清除 session/snapshot，但 `.kpatch-backup` 留在原地；下一次连接永远因非 Official 被拒绝。重新打开客户端也无效。真正升级也会保留旧备份并导致同样的再接管阻塞。
- 最小方案：记录并校验原始 hash，区分“尚未应用/已恢复”和“真实升级或未知改变”。目标已等于原始内容时允许幂等完成清理；未知升级保留/归档证据并返回需要处理的明确状态，不应一边宣告恢复完成一边留下不可再次连接的状态。

## B4 · P1：Mac 允许选择改名的应用包，但运行检测硬编码 Kiro.app

- 证据：`D:/Desktop/kiro byok/crates/desktop-host/src/backend.rs:37-43` 接受通过安装检查的自定义目录；`D:/Desktop/kiro byok/crates/patch-engine/src/detect.rs:140-150`、`:246-252` 依据目录内结构查找执行文件，不要求包名为 Kiro.app。相反 `D:/Desktop/kiro byok/crates/patch-engine/src/runtime.rs:119-122` 仅接受两个 `/Kiro.app/Contents/MacOS/...` 后缀，`:111-114` 在有其他进程但不匹配时返回 Stopped；`D:/Desktop/kiro byok/crates/patch-engine/src/process.rs:104-105` 据此直接跳过关闭。
- 触发：Mac 将有效包改名为 `Kiro Preview.app` 等，通过自定义路径选中并运行，系统进程路径反映改名后的包。
- 影响：运行中的目标被判为 Stopped，原本保护写 token、改设置及扩展的运行边界失效。使用 Electron 主程序时内存根进程识别也依赖 `/kiro.app/...`，可能漏计（`D:/Desktop/kiro byok/crates/patch-engine/src/mem_guard.rs:132-137`）。Windows 对根进程比较 Kiro.exe，不受安装父目录改名这一具体条件影响。
- 最小方案：检测/关闭/采样共享已选安装的规范化执行路径或包身份，并保守识别相关子进程。短期可明确拒绝无法安全识别的改名包，不能默默视为停止。
- 边界：未在 Mac 实机复现；后缀比较与安装接受条件的不一致由源码直接证明。

## B5 · P2：30 秒退出与 125 秒前端超时都不是操作的端到端上限

- 证据：`D:/Desktop/kiro byok/crates/patch-engine/src/process.rs:119-133` 在启动计时器之前同步等待 PowerShell/osascript 的 `output()`；Mac 的退出 Apple Event 可等待用户保存/自动化交互。`D:/Desktop/kiro byok/crates/desktop-host/src/main.rs:20-23` 整个 dispatch 持有同一个 operation 锁，连 status/heartbeat/doctor 也需此锁。`D:/Desktop/kiro byok/apps/desktop-ui/src/App.tsx:32-33` 的 Promise.race 不取消宿主调用；`:64` 超时 catch 又无期限等待 `refresh()`，直到等待完成才切换诊断页面。
- 触发：退出辅助进程阻塞或延迟超过预期；例如 Mac 退出确认迟迟未完成，或 Windows 的辅助 PowerShell 卡住。具体平台交互等待时长未实测。
- 影响：宣称 30 秒的关闭可能远超 30 秒；125 秒之后 UI 虽标记 uncertain，但仍保持 connecting/busy，诊断与状态请求排在被阻塞操作之后。若宿主后来继续，还可能在前端已超时后继续应用配置。
- 最小方案：从关闭请求开始使用单一 deadline，对辅助进程进行有界等待，超时仅终止辅助进程而非强杀 IDE；返回未确认状态。前端超时必须先结束 busy/展示结果未确认，状态查询另设有限等待。不要仅对修改 future 套 timeout 然后允许并发重试。

## B6 · P2：持久化 CA 只用于再启动 IDE，额度/刷新/解绑仍依赖启动环境

- 证据：`D:/Desktop/kiro byok/crates/patch-engine/src/desktop.rs:43-53`、`:155` 保存 CA 副本与路径；`:264-267` 再启动 IDE 使用 session.ca_path。额度请求 `:78-95` 使用 AuthClient 或无参数 client_builder；解绑 `:308-311` 同样创建 AuthClient。`D:/Desktop/kiro byok/crates/patch-engine/src/auth.rs:99-104`、`D:/Desktop/kiro byok/crates/patch-engine/src/http.rs:15-30` 都只读取进程环境 `KIRO_GATEWAY_CA_CERT`。另有 `D:/Desktop/kiro byok/crates/desktop-host/src/backend.rs:294-300` 的环境 CA 前置检查。
- 触发：使用非系统信任 CA 连接成功后，退出/重启宿主并从 Finder/桌面图标启动，未带原环境变量；或者原 CA 文件删除但会话保留副本尚在。
- 影响：同一持久会话仍可给 IDE 注入 CA，却无法获取额度、刷新令牌或解绑；原路径失效时宿主前置检查甚至先拒绝请求。不是绕过 TLS 校验，而是信任配置恢复不完整。
- 最小方案：为会话请求显式传入经校验的 session.ca_path，认证刷新/额度/解绑共享这一路径；初次登录仍使用显式配置。宿主前置检查应采用相同 CA 来源规则，保持证书校验开启。

## B7 · P2：切换卡密不重置用量状态，旧错误会遮蔽新卡的已验证余额

- 证据：`D:/Desktop/kiro byok/apps/desktop-ui/src/App.tsx:24` 将 usageState=error/loading 视为余额不可用；`:39` 请求失败设置 error；`:68` 还原/切换时清空 usage/auth，但未重置 usageState；`:55` 新卡验证只更新 auth，不清理旧 usageState；`:86` 概览因此把新余额/总额也渲染为占位符并显示旧错误。`:53` 在尚未配置且不在设置页时不会启用轮询。
- 触发：A 卡额度查询失败后，成功还原并切换到 B 卡，B 卡验证返回有效余额，但尚未启用连接。
- 影响：B 卡的新鲜授权余额被 A 卡留下的失败状态隐藏，继续显示“用量刷新失败”；新验证本身不能消除此状态。不是发现跨卡泄漏，而是 React 状态生命周期错配。
- 最小方案：清理会话与新验证成功时将 usageState 重置为 idle；给异步额度请求增加会话代次标识，忽略过期返回，使数据和状态一起切换。

## B8 · P2：额度响应没有字节/行数上限，可放大到宿主与 WebView 内存

- 证据：`D:/Desktop/kiro byok/crates/patch-engine/src/desktop.rs:91-107` 将响应直接 `.json()`，只有时间限制，没有响应体大小限制；`D:/Desktop/kiro byok/crates/desktop-host/src/backend.rs:142-148` 的 select_rows 对数组全量 clone，`:277-288` 保留所有 daily/models 行后经 IPC 返回。UI `D:/Desktop/kiro byok/apps/desktop-ui/src/App.tsx:36-38` 将完整对象存入 state，`:73` 仅在展示时对 daily 做 slice，不限制存储量。对照同宿主 verify_card 在 `backend.rs:221-234` 分块读取并限制 65536 字节。
- 触发：网关异常、历史聚合未限长，或返回超大 daily/models/无关字段的 JSON；20 秒内也可以返回很大的数据。
- 影响：在字段过滤前宿主已分配完整响应/JSON，过滤时进一步复制选中字段，经 IPC 再进入 JS 堆；轮询可能反复造成高内存或 OOM。内存整理 Kiro 工作集不能解决宿主自身分配。
- 最小方案：读取时实施累计字节上限，不能只信 Content-Length；对 daily/models 限定最大行数和字符串长度，只返回 UI 所需窗口。超过限额明确报错，不把截断结果当完整结算数据。
