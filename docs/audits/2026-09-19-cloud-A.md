### A-01 [P2] 预留 TTL 短于可达的请求总生命周期，活跃流被回收后无法结算

**主要位置**：`D:\Desktop\kiro byok\crates\gateway\src\facade\conversation.rs:402`，`D:\Desktop\kiro byok\crates\billing\src\engine.rs:2197`，`D:\Desktop\kiro byok\crates\billing\src\engine.rs:1870`。

**事实与调用链**：

- conversation.rs:402 在上游启动之前固定预留 660 秒。
- `D:\Desktop\kiro byok\crates\gateway\src\provider\retry.rs:51` 为启动重试单独设 150 秒预算；:77 每次启动最多 65 秒。失败后下一次 HTTP 请求重新开始。
- `D:\Desktop\kiro byok\crates\gateway\src\provider\governance.rs:314` 为所选 key 的请求配置 600 秒；`D:\Desktop\kiro byok\crates\gateway\src\provider\openai.rs:281` 将该期限应用于本次 HTTP 请求。`D:\Desktop\kiro byok\crates\gateway\src\watchdog.rs:42` 的 600 秒 hard timeout 同样不是从预留建立时起算。
- `D:\Desktop\kiro byok\crates\gateway\src\main.rs:308` 每 30 秒执行 janitor。`D:\Desktop\kiro byok\crates\billing\src\reservation.rs:105` 仅按 Held 和过期时间判定；engine.rs:2197–2208 不判断活跃流，在没有 pending settlement 时直接释放额度并改成 Released。
- 结算直到流结束才调用：`D:\Desktop\kiro byok\crates\gateway\src\stream.rs:318`。engine.rs:1870–1873 遇 Released 直接返回，早于 :1978 的 pending settlement 写入。因此这不是“已经持久化，等待重试”的失败。
- 当前 gateway 源码无 `extend_reservation` 调用。main.rs:327 的服务响应超时不为已返回的流式 body 建立同一生命周期的计费租约。

**触发条件**：例如单 key 启动前两次各约 60 秒后失败，第三次在总启动预算内快速产出首个 delta；第三次持续输出约 570 秒。总历时约 690 秒以上，但第三次自身小于 600 秒，且持续输出不触发 idle timeout。若 janitor 在预留到期后、流结算前运行，即进入上述分支。无需假设慢客户端；慢客户端背压可能扩大窗口，但未作为本条成立前提。

**用户/业务影响**：用户已收到内容，最后却收到结算异常；已产生的调用缺少 Usage 扣费和可重试 pending 记录，运营方承担未入账的上游成本。释放后的预留也不再计入该卡 Held 并发数，旧流仍在工作时可受理新调用。

**最小修复方向**：使预留租约覆盖从 reserve 开始的完整生命周期，或由活跃请求续租并让 janitor 区分活跃与孤儿预留。优先统一请求总 deadline，并确保所有结束路径在释放前结算；不要只把 Released 后的结算异常当成可重试 pending，也不要仅盲目增加 TTL 而不约束 body 背压。

**事实/推测/未验收**：时间预算与 Released 拒绝结算为静态事实；具体模型是否持续输出这么久、实际发生频率未知。未做时钟驱动或长流验收。建议后续用受控时钟覆盖“启动重试 + 长流 + janitor”，确认账本恰好一次、并发槽不提前释放。

### A-02 [P2] 管理台没有接入调账幂等键，响应丢失后的重试再次加减余额

**事实与调用链**：

- App.tsx:241 提交；:249–251 在网络/读取响应失败时显示“调账失败”，保留原表单并解除 mutationBusy，允许再次提交。按钮忙状态只能防在途重复点击，不能处理提交结果不确定。
- `D:\Desktop\kiro byok\crates\gateway\src\facade\admin.rs:1269` 接受无幂等键；:1304–1310 将 None 传入计费引擎。

**触发条件**：第一次调整已经持久化，但 HTTP 响应未被浏览器成功读取；管理员看到失败后，在同一表单再次确认提交。比如一次 +10 积分最终执行两次。负向调整在余额充足时同理。

**用户/业务影响**：同一操作意图重复入账，导致额外赠送额度或重复扣减用户余额。后端已有幂等支持，并不能保护当前管理台路径。

**最小修复方向**：在一次调账操作意图建立时生成 key，通过现有 idempotencyKey 字段发送；失败重试沿用原 key，只有明确的新操作才生成新 key。对结果不确定显示核对提示；可考虑要求管理台调账必须携带 key。每次点击重新生成 key 无法修复本问题。

**事实/推测/未验收**：缺失 key 和重试形成独立账本变更是事实；网络响应丢失是触发条件，并非已发生事件。未做网络故障注入；建议后续验收“服务端已提交、客户端未收到响应、重试”只改变一次余额。

### A-03 [P2] 已消费 refresh token 的防重放记录只在内存，进程重建后旧令牌重新可用

**主要位置**：`D:\Desktop\kiro byok\crates\gateway\src\auth.rs:188`，同文件 `:396`、`:406`。

**事实与调用链**：

- `D:\Desktop\kiro byok\crates\gateway\src\main.rs:178` 使用 `AuthState::with_billing`；auth.rs:188 在每次构造时建立空的 used_refresh_tokens 集合，没有从 BillingEngine 恢复消费记录。
- `D:\Desktop\kiro byok\crates\gateway\src\facade\oauth.rs:444` 的刷新入口调用 rotate_refresh_token，签发 1 小时 access 和 30 天 refresh。
- auth.rs:368–385 校验 JWT、卡状态、卡 token_version 和组；:396–406 只在内存集合检测并记录 JTI。
- :387–390 明确不使用卡级 refresh_version 进行轮换失效，:409 保留旧 refresh_version。当前过程没有持久化单个刷新令牌的消费状态。

**触发条件**：某 refresh token 已成功消费但尚未到期；之后进程重建，沿用相同签名密钥及卡状态/token_version；再次提交此前消费过的原 token。空集合使它再次通过并签发新令牌。

**用户/业务影响**：刷新令牌轮换的防重放保证跨进程生命周期失效。持有旧令牌副本的人可重新取得有效会话，直到令牌过期或卡版本被撤销。不是无凭据登录，也不绕过解绑、封禁或其他已递增 token_version 的动作。

**最小修复方向**：将 refresh JTI 消费状态持久化并原子消费，或持久化每个会话的当前刷新标识；与签发新令牌的一致性一起处理。保持会话级粒度，不通过每次刷新递增整卡版本来破坏其他合法会话。

**事实/推测/未验收**：集合清空、仅内存消费及重新通过的分支为事实；旧令牌泄露和实际进程重建事件没有调查，不作线上推断。未执行重启/重放验证；建议后续验收在同密钥和同卡快照下重建 AuthState 后旧 token 仍拒绝。
