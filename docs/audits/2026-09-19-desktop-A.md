## 1. [P1] 异常退出留下操作锁，重启后恢复操作仍被拒绝

**位置：** [snapshot.rs:324](<D:/Desktop/kiro byok/crates/patch-engine/src/snapshot.rs:324>)、[desktop.rs:55](<D:/Desktop/kiro byok/crates/patch-engine/src/desktop.rs:55>)、[desktop.rs:280](<D:/Desktop/kiro byok/crates/patch-engine/src/desktop.rs:280>)。

- **触发：** 连接、恢复或用量请求持有 `OperationLock` 时，宿主崩溃、被强制结束或机器断电。
- **证据与影响：** 锁依赖 `create_new(true)` 创建文件，仅在 `Drop` 删除；未记录所有者或提供重启恢复机制。恢复入口自身也先获取同一会话锁，因此即使备份完整，重启后仍无法从客户端恢复。
- **最小修复：** 使用进程退出即释放的 OS 文件锁；不能简单无条件删除锁文件。

## 2. [P1] 注入中途失败后，“恢复成功”仍留下永久阻断再次连接的备份

**位置：** [patch.rs:244](<D:/Desktop/kiro byok/crates/patch-engine/src/patch.rs:244>)、[patch.rs:287](<D:/Desktop/kiro byok/crates/patch-engine/src/patch.rs:287>)、[snapshot.rs:301](<D:/Desktop/kiro byok/crates/patch-engine/src/snapshot.rs:301>)、[snapshot.rs:165](<D:/Desktop/kiro byok/crates/patch-engine/src/snapshot.rs:165>)。

- **触发：** `.kpatch-backup` 创建后，状态文件写入或替换 `extension.js` 失败，原扩展仍无补丁标记。
- **证据与影响：** 此状态被识别为 `UpgradeDetected`；`restore()` 返回 `Ok(false)` 且保留备份，上层却继续删除快照、恢复凭据并报告成功。下次连接因补丁状态不是 `Official` 被拒绝，继续点击恢复也不会处理孤立备份。
- **最小修复：** 区分“未提交注入”和“真正升级”；原文件与完整备份一致时可安全清理，否则保留可操作的恢复状态，不报告恢复完成。

## 3. [P1] 前端超时后永久锁死修改与正常退出，后端完成也无法解除

**位置：** [App.tsx:29](<D:/Desktop/kiro byok/apps/desktop-ui/src/App.tsx:29>)、[App.tsx:56](<D:/Desktop/kiro byok/apps/desktop-ui/src/App.tsx:56>)、[main.rs:159](<D:/Desktop/kiro byok/crates/desktop-host/src/main.rs:159>)。

- **触发：** 写操作超过 125 秒，随后后端完成或返回失败，且仍存在待恢复记录。
- **证据与影响：** `Promise.race` 只停止前端等待；`mutation.current` 与 `uncertain` 一旦置为 `true`，没有清除路径。所有 `ask()` 操作，包括恢复、退出，均被拒绝。托盘遇到恢复记录也只重新触发同一退出事件；关闭窗口只是隐藏，无法按提示正常“重新打开客户端”解决。
- **最小修复：** 保留原始请求的最终结果并提供操作完成状态查询；确认后台已结束后允许恢复，不因单纯超时永久禁用退出流程。

## 4. [P2] 关闭 IDE 的“30 秒超时”没有覆盖实际退出命令

**位置：** [process.rs:109](<D:/Desktop/kiro byok/crates/patch-engine/src/process.rs:109>)、[process.rs:120](<D:/Desktop/kiro byok/crates/patch-engine/src/process.rs:120>)、[process.rs:133](<D:/Desktop/kiro byok/crates/patch-engine/src/process.rs:133>)、[main.rs:21](<D:/Desktop/kiro byok/crates/desktop-host/src/main.rs:21>)。

- **触发：** macOS `osascript` 退出请求等待保存对话框、Apple Event 响应等；Windows 退出辅助命令阻塞也存在同类问题。
- **证据与影响：** 同步 `.output()` 返回以后才创建 30 秒计时器，因此该超时不是完整关闭流程的上限。等待期间宿主持有全局操作锁，状态、诊断、心跳请求也排队，前端超时无法取消后台等待。
- **最小修复：** 从调用辅助命令前设置统一截止时间，监督辅助子进程并回收；超时仅停止辅助程序，不强杀用户 IDE。

## 5. [P2] 保存的私有 CA 未用于后续用量、刷新和解绑请求

**位置：** [desktop.rs:43](<D:/Desktop/kiro byok/crates/patch-engine/src/desktop.rs:43>)、[desktop.rs:78](<D:/Desktop/kiro byok/crates/patch-engine/src/desktop.rs:78>)、[desktop.rs:309](<D:/Desktop/kiro byok/crates/patch-engine/src/desktop.rs:309>)、[http.rs:15](<D:/Desktop/kiro byok/crates/patch-engine/src/http.rs:15>)。

- **触发：** 使用私有 CA 成功连接，之后从普通桌面入口重启宿主，不再带原先的 `KIRO_GATEWAY_CA_CERT` 环境变量。
- **证据与影响：** 会话已持久化 CA 副本和 `ca_path`，但 HTTP 客户端仍仅从当前环境变量加载 CA；会话 CA 只在重新启动 IDE 时被使用。对应私有 CA 网关的用量、令牌刷新和解绑会发生证书校验失败。
- **最小修复：** 会话网络操作显式使用持久化 CA 路径，统一传给 `AuthClient` 和用量客户端，继续保留正常证书校验。
