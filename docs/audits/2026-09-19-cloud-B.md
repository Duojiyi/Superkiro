## B-01 [P1] 刷新令牌消费记录未持久化，重启后恢复重放能力

位置：`crates/gateway/src/auth.rs:160`、`:183–190`、`:397–406`；生产装配 `crates/gateway/src/main.rs:177–178`；公开刷新入口 `crates/gateway/src/facade/oauth.rs` 中的 `rotate_refresh_token(&raw_rt, 3600, 30 * 86400)` 调用。

触发：先成功使用刷新令牌 R 取得下一对令牌，再重启网关；AUTH_SECRET、卡 token_version 和卡有效状态保持不变，R 尚未过期。再次提交 R。

证据：with_billing 每次创建空的 used_refresh_tokens HashMap；轮换只用此表检查并插入 JTI，没有把消费结果写入 BillingEngine。刷新版本也没有在轮换时与持久化版本比较或递增。重启后同一签名仍有效，但已消费记录不存在。

影响：已轮换淘汰的刷新令牌在重启后重新可用。曾取得旧令牌的一方能重新创建访问会话，破坏刷新令牌单次使用保证。卡级撤销仍有效，不能据此声称被封禁或已经换绑撤销的令牌也可恢复。

最小修复：将已消费刷新令牌 JTI 及过期时间纳入持久化状态，在同一个原子操作中检查并消费，提交成功后才返回新令牌；按过期时间清理。保留每令牌轮换，避免用卡级版本误撤销其他有效会话。

## B-02 [P1] 存储的卡密哈希本身被公开入口当作卡密接受

位置：`crates/billing/src/engine.rs:1288–1298`，尤其 `:1297`；登录 `crates/gateway/src/facade/oauth.rs:190`；门户查询 `crates/gateway/src/facade/portal.rs:219`、`:257`，激活/解绑/充值入口 `:312`、`:510`、`:639`。

触发：取得某张卡的 code_hash，但不知道原始卡密。向门户查询或登录接口提交该哈希作为 card/card_key。对已绑定卡，门户查询还会返回 bound_devices，可用于满足登录的 device_id 检查；卡的正常状态、有效期等检查仍需通过。

证据：公开查找同时允许 SHA256(输入) == code_hash 和 输入 == code_hash。后一分支直接把数据库中的验证值变成可重放凭据，公开接口并未禁用它。

影响：一旦卡密哈希从快照解密结果、内部数据导出或其他只读访问渠道泄露，不需要破解卡密就可进入公开业务接口。此处确认的是 pass-the-hash 行为，不是声称已找到匿名读取哈希的接口，也不意味着加密快照可被直接解密。

最小修复：公开 find_card_by_secret 只比较 SHA256(原始输入) 与存储哈希。确有平台兼容需求时，另建内部哈希查找函数，限制于已认证的内部调用，不复用为公开认证函数。

## B-03 [P2] 导入供应商丢弃租户归属，重导入会清空专属绑定

位置：`crates/gateway/src/facade/provider_import.rs:221–228`、`:241–245`；`crates/gateway/src/provider/import.rs:63–68`；`crates/billing/src/provider.rs:57`；`crates/billing/src/engine.rs:1464–1467`。权限解释：`crates/billing/src/group.rs:72–73`，实际路由检查 `crates/gateway/src/facade/conversation.rs:799`。

触发：通过管理员导入接口指定 target_group_id；或对已经具有 group_id 的专属供应商，以同一个供应商 ID 重导入新地址/密钥。

证据：接口解析 target_group 后执行 let _ = target_group。转换函数总是调用 Provider::new，其 group_id 固定为 None。持久化按 ID 整体覆盖 Provider，运行时也注册该新对象，没有保留旧 group_id。

影响：新导入不兑现指定专属归属；重导入会把既有专属供应商变成共享供应商。原专属组访问检查失败，已发布映射可能直接不可用；共享组的供应商访问检查则变为允许。这里不声称导入会自动发布用户模型目录，共享组实际调用还受模型/Key 权限及路由条件约束。

最小修复：更新既有供应商时默认保留 group_id；显式传入 target_group_id 时校验组存在并应用到持久化及运行时同一对象。若暂不支持专属导入，应明确拒绝该参数，而非静默忽略；不要在普通密钥更新中隐式改变归属。

## B-04 [P2] 失败冷却从请求开始计时，慢失败后冷却已过期

位置：`crates/gateway/src/facade/conversation.rs:785–789`、`:853–859`；`crates/gateway/src/provider/governance.rs:359–362`、`:298`；`crates/billing/src/provider.rs:185–187`；单次预读取超时 `crates/gateway/src/provider/retry.rs:77`。

触发：例如一个有多个 Key 的池，首个 Key 的上游连接/响应头阶段一直挂起，由 start_stream 的 65 秒尝试期限终止。该失败随后进入治理层的冷却分支。用多 Key 场景可避免依赖单 Key 内部重试及外层总期限的竞争。

证据：网关在调用上游前取得 now_secs，并传入 60 秒冷却长度；失败分支仍将旧 now_secs 传给 mark_key_failure。后者设置 cooldown_until = now_secs + 60。65 秒后才观察到失败时，此期限已经过去；下次 select_key_for_model 又用当前时刻检查，故该 Key 立即符合冷却时间条件。Degraded 本身不是永久禁选状态。

影响：慢失败的 Key 没有得到实际的失败后冷却，后续独立请求可再次选中它并重复等待，放大延迟与上游故障压力；较短失败也会按请求耗时缩短冷却。

最小修复：在标记失败时读取当前时间，使用失败发生时刻计算 cooldown_until；仍可保留注入时间接口用于确定性校验，但时间值须在失败处采样。

## 未提升为确证问题的候选

- 无输出失败扣费：stream.rs 的局部分支确有差异，但生产路径 retry::start_stream 在首个 Delta 前缓存事件并丢弃失败尝试的 usage。未证明普通输入 usage 后立即报错能穿透此前置逻辑，因此不按该简化场景报缺陷。客户端断连及工具片段的计费策略也不能仅凭此处推定违规。
