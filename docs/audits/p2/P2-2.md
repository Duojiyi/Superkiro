## 审计 B：对抗性盲审 (Adversarial Blind Audit)

针对换绑穿透、多设备竞态、重放攻击、冻结封号即时拦截等极端对抗场景构造对抗测试：

### 对抗场景 1：设备满载下的换绑配额耗尽与冷却对抗
- **测试**：`test_rebind_eviction_cooldown_and_limit`
- **攻击**：构造 2 设备上限、2 次换绑配额、300 秒冷却的卡密：
  1. 绑定 `dev-1`, `dev-2`（成功，未耗配额）；
  2. 尝试换绑 `dev-3`，成功淘汰 `dev-1`，消耗 1 次换绑配额，`token_version` 自增；
  3. 在 300 秒冷却期内（$t=1200$）尝试换入 `dev-4`，BillingEngine 严格拒绝并返回 `RebindCooldown { remaining_secs: 150 }`；
  4. 冷却期过后换入 `dev-4` 成功，换绑配额用尽（2/2）；
  5. 再次尝试换绑 `dev-5`，直接拦截返回 `RebindLimitExceeded { current: 2, max: 2 }`，无法继续换绑。
- **实测结果**：**PASS**。

### 对抗场景 2：设备指纹解绑与会话吊销联动
- **测试**：`test_unbind_device`
- **攻击**：解绑指定设备时，确保非绑定设备报错 `DeviceNotFound`，解绑合法设备成功后自增 `token_version` 切断已移除设备的会话。
- **实测结果**：**PASS**。

### 对抗场景 3：冻结、解冻与封号全链路阻断
- **测试**：`test_freeze_unfreeze_and_ban_lifecycle` & `test_batch_card_status_operations`
- **攻击**：
  1. 冻结卡密 -> 状态变 `Frozen`，`token_version` 自增；
  2. 正常时间解冻 -> 恢复 `Active`；
  3. 超过 `valid_until` 后解冻 -> 状态自动流转为 `Expired` 防止时钟穿透；
  4. 封禁卡密 -> 状态变为 `Banned`，`token_version` 递增彻底吊销；
  5. 批量冻结、解冻与封号操作 100% 成功。
- **实测结果**：**PASS**。

### 对抗场景 4：充值卡重放攻击与过期卡顺延复活
- **测试**：`test_topup_generation_export_and_redemption` & `test_topup_reactivates_expired_card`
- **攻击**：
  1. 单张充值卡兑换后，再次提交相同明文充值卡，系统即刻返回 `InvalidOrRedeemedTopupCode` 拒绝重复核销；
  2. 针对已过期的卡（原过期时间 5000，当前时间 10000），兑换 7200 秒充值卡，新有效时间并非在 5000 基础上累加（避免充值仍过期），而是以当前时间 10000 为基点顺延至 17200，并自愈恢复状态为 `Active`；
  3. 账本中精确落入 `LedgerKind::Topup` 审计条目。
- **实测结果**：**PASS**。

### 对抗场景 5：批量充值卡导出格式审计
- **测试**：`test_topup_batch_and_csv_json_export`
- **实测结果**：批量生成高熵充值卡，CSV 包含必要列，JSON 能够正常序列化反序列化。**PASS**。
