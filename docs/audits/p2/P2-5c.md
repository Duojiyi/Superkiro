## 审计 A：规范盲审 (Spec Blind Audit)

对照系统架构规范 Spec §5（数据模型与状态机）、Spec §14.9（未激活卡密作废回收与生命周期管理）以及 Spec §14.10.5（调账与账本不可篡改性）逐项核验：

| 规范章节 | 规范条款与要求 | 代码落地位置 | 审计结论 |
| :--- | :--- | :--- | :---: |
| **Spec §14.9** | **人工调账走账本**：运营给卡密补积分/扣积分时，必须以账本条目形式写入（`usage_ledger` 增加 `kind=adjustment` 条目 + 操作人 `operator_id` + 原因 `reason`），不直接改余额字段，保证账实相符、可追溯。 | `crates/billing/src/engine.rs::adjust_balance`, `reconcile_card_balance` | **PASS** |
| **Spec §14.9** | **未激活卡密作废回收**：未激活卡密可作废并回收到库存（状态迁移至 `Voided`，更新备注审计信息，即时失效 `token_version`）；已激活卡密只能冻结/封禁（不做按比例退款），禁止作废。 | `crates/billing/src/card.rs::CardStatus::Voided`, `engine.rs::void_unactivated_card` | **PASS** |

| **Spec §5 & §14.10.5** | **调账边界防击穿**：调减积分（扣除）不能超过当前可用余额（`available_credits`），禁止造成非法负可用额度；参数必须非空（禁止空 operator 或空 reason 或 0 调账）。 | `crates/billing/src/engine.rs::adjust_balance` | **PASS** |

| **Spec §5 & §6.1** | **账实一致数学对账器**：提供 `reconcile_card_balance`，严格对比 初始积分 + 充值总额 + 调账增量 == `credit_total`，且 实际用量 + 调账扣减 == `credit_used`，确保全周期可复核。 | `crates/billing/src/engine.rs::reconcile_card_balance`, `CardReconciliation` | **PASS** |

## 审计 B：对抗性盲审 (Adversarial Blind Audit)

在 `crates/billing/tests/adjustment_void_test.rs` 中编写 10 个独立对抗测试用例，覆盖异常输入、越界扣减、并发安全、状态冲突及数学对账：

### 对抗场景 1：人工正向调账（补偿/奖励）与审计字段固化
- **测试**：`test_manual_adjustment_positive_credit_grant`
- **验证**：给卡密补发 50 积分（50,000,000 微积分），操作人 `"operator-ops-1"`，原因 `"Goodwill compensation for downtime"`。
- **实测**：账本生成 `kind = Adjustment`，`credits_charged = 50,000,000`，`operator_id` 与 `reason` 严格记录；卡密 `credit_total` 提升至 150 积分，可用额度同步增加。**PASS**。

### 对抗场景 2：人工反向调账（扣减/退款冲正）
- **测试**：`test_manual_adjustment_negative_deduction`
- **验证**：对卡密扣减 30 积分，操作人 `"operator-finance-1"`，原因 `"Manual deduction for offline refund"`。
- **实测**：账本记录负值扣减，卡密 `credit_used` 自增 30 积分，可用额度从 100 降为 70 积分。**PASS**。

### 对抗场景 3：恶意/误操作超额扣除防御（防余额击穿）
- **测试**：`test_manual_adjustment_insufficient_credit_rejection`
- **验证**：卡密仅有 50 积分可用额度，操作员试图调减 60 积分。
- **实测**：系统返回 `BillingError::Card(CardError::InsufficientCredit)` 拒绝执行；卡密余额未变动，账本未追加孤儿条目，保证原子一致性。**PASS**。

### 对抗场景 4：参数安全守卫与输入校验
- **测试**：`test_manual_adjustment_validation_guards`
- **验证**：
  1. 调账额度为 0 -> 拒绝 `InvalidAdjustment`；
  2. 操作人为空白字符 -> 拒绝 `InvalidAdjustment`；
  3. 原因理由为空白字符 -> 拒绝 `InvalidAdjustment`；
  4. 目标卡密不存在 -> 拒绝 `CardNotFound`。
- **实测**：四大守卫全部拦截，拒绝任何无审计留痕的伪操作。**PASS**。

### 对抗场景 5：账实相符与数学收敛闭环验证
- **测试**：`test_ledger_reconciliation_mathematical_consistency`
- **验证**：混合执行 1 次真实模型调用结算（扣除）、1 次续费码充值（+50 积分）、1 次正向补偿（+20 积分）、1 次反向纠偏（-10 积分）。调用 `reconcile_card_balance`。
- **实测**：
  `expected_credit_total == actual_credit_total == 170M micro-credits`
  `expected_credit_used == actual_credit_used == usage + 10M micro-credits`
  `is_balanced == true`
  账实 100% 吻合无漂移。**PASS**。

### 对抗场景 6：未激活卡密作废与生命周期变更
- **测试**：`test_void_unactivated_card_success`
- **验证**：从未激活模板批次中取卡作废，操作人 `"operator-inventory-1"`，原因 `"Batch misprint recycling"`。
- **实测**：状态迁移至 `CardStatus::Voided`，备注追加 `[VOIDED by operator-inventory-1 at ...]`，`token_version` 自增保证潜在预签 Token 立即失效。**PASS**。

### 对抗场景 7：作废卡密防激活攻击
- **测试**：`test_voided_card_cannot_be_activated`
- **验证**：对已作废卡密尝试调用 `card.activate()` 模拟黑产或用户撞库激活。
- **实测**：系统直接拒绝 `Err(CardError::NotActive(CardStatus::Voided))`，杜绝死卡复活。**PASS**。

### 对抗场景 8：已激活/使用卡密禁止作废（对照 Spec §14.9 硬约束）
- **测试**：`test_cannot_void_activated_or_used_card`
- **验证**：分别对 `Active`, `Frozen`, `Banned`, `Expired` 状态的卡密尝试作废。
- **实测**：全部返回 `BillingError::CannotVoidActivatedCard` 拒绝，严格遵循“未激活卡密可作废回收，已激活只能冻结/封禁”的商业风控底线。**PASS**。

### 对抗场景 9：批量作废混合态容错测试
- **测试**：`test_batch_void_unactivated_cards`
- **验证**：传入 3 张卡（2 张未激活，1 张已激活）。
- **实测**：2 张未激活卡成功作废为 `Voided`，已激活卡安全返回错误，批处理不发生级联崩溃或状态污染。**PASS**。

### 对抗场景 10：卡密库存分类精算与隔离检索
- **测试**：`test_card_inventory_tracking_by_template_and_status`
- **验证**：批量生成 5 张卡，作废 2 张，激活 1 张。
