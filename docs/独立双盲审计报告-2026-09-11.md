## 1. 执行摘要

项目的主要问题不是单一实现缺陷，而是“安全边界、管理端、后端接口”三者没有形成同一套可运行系统：

1. 管理端 `apps/admin-ui/src/App.tsx` 是静态演示界面，所有业务操作均为本地 React 状态或 Toast，没有调用后端 API；页面显示的卡密、Provider、财务、KEK 和审计结果不是后端真实数据。
2. 部署文件把 `/admin` 静态页面公开挂载到 Caddy，但没有管理员登录、会话、CSRF、权限校验或登出机制；页面上的“退出”只显示 Toast。
3. 后端存在默认 JWT 密钥、默认开发卡和 0 配置时放行的卡平台认证，任一部署疏忽都会直接转化为伪造凭证或未授权发卡能力。
4. 自助门户的查询、激活、解绑、充值接口公开暴露，当前代码未见统一的 IP/卡密维度限流、失败退避或审计关联，存在枚举、撞库、解绑和充值券滥用风险。
5. 测试覆盖大量“理想路径和单元行为”，但没有覆盖真实反向代理部署、管理端鉴权、默认配置拒绝启动、跨接口授权矩阵、限流、并发持久化和前后端契约一致性。

## 3. P0 发现

### P0-01 管理端是不可用的演示 UI，所有高风险操作均未落库

**证据**：`apps/admin-ui/src/App.tsx:9-15,17-20,103,198,232-243,293-350,450-507,552-627`。文件只使用 `useState`，没有 `fetch`、XHR、WebSocket、EventSource 或 API client；按钮只调用 `showToast`、打开 modal 或修改本地状态。

**影响**：管理员看到的卡密、余额、Provider、模型价格、调用链和财务报表不是后端事实；“冻结”“解绑”“调账”“KEK 轮换”“发布公告”“导出”等操作不会执行。运营人员可能据此做出错误账务或安全判断，且页面对外呈现了功能已完成的假象。

**修复要求**：先定义版本化 API 契约，再接入真实查询和 mutation；每个 mutation 必须带管理员身份、权限、幂等键、服务端结果回显和失败状态。删除所有模拟成功 Toast，未接入的功能必须显示不可用状态。

### P0-02 `/admin` 管理界面公开可访问，且没有真正的管理员认证

**证据**：`deploy/Caddyfile:6-20` 直接 `file_server` 提供 `/admin*`；`deploy/docker-compose.yml:29-45` 将其暴露在 80/443；`apps/admin-ui/src/App.tsx:103` 的退出按钮只显示 Toast。后端的 `security.rs` 仅提供可复用的隔离 helper，并未在 `main.rs` 中建立独立 9090 管理监听器；实际路由由 `registry.into_router_with_auth` 统一生成。

**影响**：任何可访问部署地址的人都能加载运营后台。即使页面目前不执行写操作，也会泄露系统能力、租户/供应商/账务界面信息，并使未来接入 API 时很容易形成“页面公开、API 误配”的直接管理面暴露。

**修复要求**：管理端必须由独立管理 listener 或经过认证的反向代理保护；后端管理 API 使用独立管理员身份、最小权限和 CSRF 防护；静态资源也应置于认证边界内，登出必须撤销服务端会话/刷新令牌。

### P0-03 默认 JWT 密钥可预测，且生产启动默认接受它

**证据**：`crates/gateway/src/main.rs:60-63` 在 `AUTH_SECRET` 缺失时使用固定字符串 `kiro-byok-single-server-secret-key-32b-ok!`；`crates/gateway/src/auth.rs:139-146` 还内置固定开发密钥和 `card-dev-001`。

**影响**：攻击者可在未配置环境变量的部署中自行签发任意 `card_id/group_id/token_version` 的 JWT；默认开发卡还提供已知身份入口。若同一默认密钥被多个实例使用，跨环境伪造也成为可能。

**修复要求**：生产环境缺少高熵密钥时拒绝启动；禁止源码内置可用于生产的开发卡和开发密钥；密钥长度、随机性、轮换、旧密钥失效和启动日志脱敏都应有测试。

### P0-04 卡平台认证配置缺失时直接放行

**证据**：`crates/gateway/src/facade/card_platform.rs:25-31`：`expected_key` 为 `None` 或空字符串时返回 `true`。`main.rs:81-84` 使用 `CARD_PLATFORM_KEY` 的 `Option` 直接注册 card platform facade；`facade/mod.rs` 将所有 `/api/v1/cards/` 路由归入 public routes。

**影响**：未设置 `CARD_PLATFORM_KEY` 的部署中，库存查询、批量拉卡、兑换回调均无认证。攻击者可消耗库存、批量取得卡密或伪造兑换回调，造成资产和账务损失。

**修复要求**：生产模式缺少 key 必须拒绝启动；测试/开发模式必须显式开关且绑定 loopback；使用常量时间比较、密钥轮换和请求签名/时间戳/nonce，避免单一静态 header 长期重放。

## 4. P1 发现

### P1-01 自助门户的敏感操作全部公开，缺少统一反滥用控制

**证据**：`crates/gateway/src/facade/mod.rs` 将 `/portal`、`/api/v1/portal/query`、`activate`、`unbind`、`topup` 归入 public routes；`portal.rs:120-404` 实现卡密查询、激活、解绑和充值；未发现统一 rate limit、失败计数、验证码、设备/来源绑定或风控门槛。

**影响**：可对卡密进行在线枚举、撞库和批量状态探测；已知卡密的解绑和充值接口可被自动化滥用。查询响应还返回余额、套餐、设备数等敏感资产信息。

**修复要求**：按 IP、卡密哈希、设备指纹和动作分别限流；失败退避和告警；敏感操作使用一次性挑战或已认证会话；响应避免区分过细的失败原因。

### P1-02 管理 API 与管理静态页面没有契约或接入关系

**证据**：后端存在 `/api/v1/admin/providers/import` 等受保护 facade，但 `App.tsx` 没有请求代码、类型契约或错误处理。前端显示“管理端口 9090”，部署只暴露 gateway/Caddy 端口。

**影响**：所谓管理功能没有可验证的端到端路径；即使后端修复了权限，前端也不会使用；即使前端后续接入，也没有编译期保证字段名、状态码和分页/错误结构一致。

**修复要求**：从后端 schema 生成或共享 API 类型；至少建立登录、当前管理员、卡密列表/冻结、Provider、账务导出和审计日志的端到端测试；将部署端口与 UI 配置统一。

### P1-03 账务状态使用明文 JSON 快照保存

**证据**：`crates/billing/src/engine.rs:220-244` 将完整 `BillingSnapshot` 用 `serde_json::to_string_pretty` 写入 `billing_state.json`；部署把 `./data` 直接挂载到容器，未见文件加密、权限校验、备份加密或完整性签名。

**影响**：宿主机备份、卷、误读权限或容器逃逸即可获得卡密关联、余额、账本和可能的供应商敏感信息；攻击者若能修改文件，可在重启时篡改账务状态。Windows/Linux rename 语义也未被跨平台验证。

**修复要求**：敏感字段按用途加密，快照做 AEAD 完整性保护并绑定版本/实例；备份加密和密钥分离；启动时拒绝篡改或回滚快照；对文件权限和恢复流程做集成测试。

### P1-04 生产服务默认监听 `0.0.0.0`，且 Compose 通过 Caddy 明确公网暴露

**证据**：`main.rs:30-32` 默认 host 为 `0.0.0.0`；Compose 设置 `HOST=0.0.0.0`，Caddy 映射 `80:80`、`443:443`；Caddy 的 `:80` 站点直接导入完整路由。

**影响**：任何错误配置都会把所有公共 facade、门户和卡平台接口暴露到公网；仅依赖“私有隔离”文字或前端提示不能构成网络边界。

**修复要求**：内部 gateway 只绑定容器网络或 loopback；仅 Caddy/管理入口暴露；生产默认拒绝明文 HTTP 或强制跳转 HTTPS；对各类 facade 单独定义暴露策略。

### P1-05 上游 API key 通过环境变量注入但缺少最小权限和泄露控制

**证据**：`main.rs:96-123` 从 `UPSTREAM_API_KEY` 读取并放入 provider config；Caddy 开启 access log（`deploy/Caddyfile:42-46`），代码中大量格式化错误和调试日志存在。

**影响**：环境、容器 inspect、崩溃转储和过宽日志权限可能泄露 key；上游 key 没有按租户/模型/额度隔离，单 key 泄露可影响全部租户。

**修复要求**：使用 secrets manager/文件描述符注入，日志统一脱敏；按 provider、租户和用途拆分 key，限制模型、来源、额度和有效期；增加 key 泄露检测和轮换演练。

### P1-06 请求路由没有展示出全局 body、超时、限流和安全 header 层的实际挂载

**证据**：`security.rs` 定义了 `BodyGuardrail`、`DualListenerRouter` 等能力，但 `main.rs` 最终只调用 `registry.into_router_with_auth(auth_state)` 后直接 `axum::serve`；未见这些 guardrail 统一挂载。

**影响**：代码中“有安全组件”不等于运行时生效。未挂载时，大请求、慢连接、暴力请求和某些响应头策略仍可能绕过预期控制。

**修复要求**：在最终 router 上显式挂载 body limit、request timeout、rate limiter、trace redaction、CORS/CSRF 和安全响应头；写真实 HTTP 集成测试验证每个 middleware 的生效顺序。

### P1-07 错误响应可能向客户端反射内部认证细节

**证据**：`auth.rs:69-72` 将 `jsonwebtoken` 错误文本拼接到返回信息；`auth.rs:79-87` 直接返回卡片不存在、状态和 token version mismatch 的内部信息。

**影响**：攻击者可区分签名错误、卡片存在性、卡片状态和当前版本，辅助卡密枚举与版本/撤销状态探测；内部错误内容也可能暴露实现细节。

**修复要求**：对外统一返回不区分资源存在性的错误；详细原因只进入脱敏、关联 request id 的内部日志；禁止把 token version、card id 和 JWT 库原始错误返回给客户端。

## 5. P2 发现

### P2-01 CI 没有构建或测试管理端，也没有安全扫描

`.github/workflows/ci.yml` 只执行 Rust fmt、clippy 和 cargo test；没有 `npm ci && npm run build`、依赖审计、镜像扫描、秘密扫描、API 契约测试或部署 smoke test。

### P2-02 前端错误处理、会话过期和并发状态都未实现

由于前端没有网络层，无法处理 401、403、409、429、网络超时、重复提交、刷新和撤销；Toast 不能作为业务成功确认。

### P2-03 已编译产物和运行/调试资产混在工作区

仓库包含 `apps/admin-ui/dist`、截图、`launch.log`、压缩部署包以及多个调试脚本。若被打包或提交，可能泄露环境信息、旧 UI、日志和供应商资产，也会让部署使用过期构建结果。

### P2-04 Caddy 安全响应头不完整

当前只有 `X-Content-Type-Options` 和 `Referrer-Policy`，未见严格 CSP、HSTS、`frame-ancestors`/X-Frame-Options、权限策略或缓存策略；管理端尤其不应允许被任意页面嵌入。

### P2-05 provider 选择存在静默降级

`main.rs:114-118` 只有 `anthropic` 才选择 Anthropic，否则所有未知 `PROVIDER_TYPE` 都降为 OpenAI。拼写错误或配置漂移不会导致启动失败，可能把请求发送到错误供应商或错误协议。

### P2-06 时间与账务恢复语义缺少跨进程一致性证明

核心状态主要依赖内存锁和单文件快照；虽有原子替换测试，但没有多进程写入、崩溃点恢复、fsync、快照版本回滚检测和备份恢复演练。单机模式下进程异常退出仍可能丢失最近账务变更。

## 7. 修复顺序

1. **立即阻断公网生产使用**：移除默认密钥和默认开发卡；`AUTH_SECRET`、`CARD_PLATFORM_KEY` 缺失时拒绝生产启动；暂时下线或加固 portal 和 card platform；锁定 `/admin`。
2. **建立真实管理安全边界**：独立 admin listener/API、管理员登录、短期会话、CSRF、RBAC、审计日志和静态资源认证。
3. **建立契约闭环**：定义 OpenAPI/共享 TypeScript 类型，接入真实查询/mutation，补 401/403/409/429/超时和幂等处理。
4. **补全运行时保护**：统一 body limit、timeout、rate limit、请求关联 ID、日志脱敏、安全 headers、CORS 策略和 provider 配置 fail-closed。
5. **保护账务与密钥**：AEAD 快照、签名/版本、防回滚、加密备份、secrets manager、key rotation 和恢复演练。
6. **把验证纳入 CI**：前端构建、依赖与镜像扫描、秘密扫描、真实 HTTP 集成测试、反向代理 smoke test、契约测试和默认配置负面测试。

## 8. 验收标准

- 空环境启动在生产模式下因缺少必需密钥明确失败，不可自动使用固定默认值。
- 未认证请求无法加载或调用管理端；管理员登出后旧会话立即失效。
- portal/card platform 的每个敏感操作都能证明限流、幂等、审计和重放防护生效。
- 管理端任何成功提示都来自服务端成功响应，并能在刷新后看到持久化结果。
- 账务快照被修改、回滚、截断或恢复到旧版本时，服务拒绝加载并留下告警。
- CI 同时通过 Rust、前端、部署 smoke、契约和安全负面测试。

## 9. 本轮整改记录（2026-09-11）

### 第一轮已完成：

- 删除 gateway 启动时的默认开发卡初始化。
- `AUTH_SECRET` 和 `CARD_PLATFORM_KEY` 改为必填，缺失或短于 32 字符时拒绝启动。
- 未知 `PROVIDER_TYPE` 改为启动失败，不再静默降级为 OpenAI。
- 卡平台接口在密钥缺失或为空时拒绝请求；相关测试已改为显式密钥并通过。
- Caddy 管理路径增加 Basic Auth 配置占位、HSTS、CSP、禁止 iframe 和 Permissions-Policy；移除重复的静态资源绕过规则。
- 认证错误对外不再返回 JWT 原始错误、卡片 ID、token version 和具体状态。
- CI 增加管理端 `npm ci` 与 `npm run build`。
- 管理端高风险按钮不再伪造"成功"，未接入后端时明确提示当前禁用；退出按钮改为跳转登出路径。

### 第二轮已完成：

- **P0-04 加固**：卡平台 API key 验证改为常量时间比较（XOR-accumulate），防止时序侧信道攻击。
- **P1-06**：全局安全 middleware 已挂载到最终 router：`DefaultBodyLimit::max(10MB)` + `TimeoutLayer(300s)`，启动日志打印确认。添加 `tower-http` 依赖。
