# Service card tiers and device policy

New admin issuance accepts `templateId`: `tier-1000` (PRO), `tier-2000` (PRO+), `tier-5000` (PRO Max), `tier-10000` (Power). Omitted template ID and `standard-monthly` select PRO+ (2000 points, 30 days starting at activation). Optional `creditTotal` is micro-credits and must match the template; optional `maxDevices` must be 1. Unknown template/group IDs are rejected. Group routing and pricing remain independent of the card display tier.

`issued_credits` is persisted on cards and does not change with charges, reservations, top-ups, or balance adjustments. Portal `virtual_plan_name` and gateway usage/subscription responses use this entitlement. These are our service tiers, not official Kiro subscriptions. Legacy records without issued entitlement display `Legacy service plan`; current balances cannot reliably reconstruct original issuance. Low-level trial/custom template constructors remain compatible and are not part of the admin tier catalog.

New cards have one device slot. Binding a device already on another card is rejected under the state transaction lock. Replacement of a sole binding retains existing rebind limits/cooldown and revokes old access tokens. Legacy cards with multiple bindings cannot activate, bind, reserve usage, or authenticate access tokens until an administrator explicitly unbinds the unwanted device(s). No device is automatically selected from a multi-binding record. Empty/single-binding legacy cards normalize capacity to 1 on successful binding. Existing unbound development/auth flows remain supported; tokens are card-level rather than cryptographically device-attested, so this is binding enforcement, not prevention of copied bearer tokens. Historical cross-card duplicate bindings require explicit administrative cleanup; no automatic migration is performed.

Runtime persistence is the existing JSON snapshot mechanism; the optional omitted field preserves legacy serialized card shape/checksum behavior. schema.sql describes fresh SQL deployments only, including max_devices=1 checks. No production migration or external API calls were performed. Existing SQL installations need a separately reviewed migration. No original entitlement is guessed or backfilled.
