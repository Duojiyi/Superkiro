# Service card tiers and device policy

New admin issuance takes `planId` (or `templateId`, its older name): a plan of the catalog published with the commercial configuration (`plans`, `removed_plans`). A state that has stored no plans has the four tiers `tier-1000` (PRO), `tier-2000` (PRO+), `tier-5000` (PRO Max), `tier-10000` (Power), 30 days from activation, one device, two requests at once. Omitted plan ID and `standard-monthly` select `tier-2000` unless a plan has that ID. Optional `creditTotal` is micro-credits and must match the plan; optional `maxDevices` must be 1, and so must the plan's. Unknown, off-sale plans and unknown or closed groups are rejected; any group that takes cards may be chosen. Group routing and pricing remain independent of the card's plan.

A card issued from the catalog keeps its plan as it was then (`plan`: ID, name, points, price, validity days, devices, concurrency, Kiro plan type), and portal `virtual_plan_name` and gateway usage/subscription responses report it. `issued_credits` is persisted on cards and does not change with charges, reservations, top-ups, or balance adjustments; a card issued before the catalog is the tier its issued credits name. These are our service plans, not official Kiro subscriptions. Legacy records without issued entitlement display `Legacy service plan`; current balances cannot reliably reconstruct original issuance. Low-level trial/custom template constructors remain compatible and are not part of the catalog.

New cards have one device slot. Binding a device already on another card is rejected under the state transaction lock. Replacement of a sole binding retains existing rebind limits/cooldown and revokes old access tokens. Legacy cards with multiple bindings cannot activate, bind, reserve usage, or authenticate access tokens until an administrator explicitly unbinds the unwanted device(s). No device is automatically selected from a multi-binding record. Empty/single-binding legacy cards normalize capacity to 1 on successful binding. Existing unbound development/auth flows remain supported; tokens are card-level rather than cryptographically device-attested, so this is binding enforcement, not prevention of copied bearer tokens. Historical cross-card duplicate bindings require explicit administrative cleanup; no automatic migration is performed.

Runtime persistence is the existing JSON snapshot mechanism; the optional omitted field preserves legacy serialized card shape/checksum behavior. schema.sql describes fresh SQL deployments only, including max_devices=1 checks. No production migration or external API calls were performed. Existing SQL installations need a separately reviewed migration. No original entitlement is guessed or backfilled.

## Desktop settled usage

`GET /getUsageLimits` adds `virtualPlanName` and `validUntil` (Unix seconds; null for perpetual), refreshed from the current card, and `settledUsage`. patch-cli `desktop-usage` returns `{success, usage, settledUsage}` with the same statistics copied to the top level, leaving the full gateway response under `usage`.

Statistics cover UTC today and the preceding 29 calendar days, from `windowStart` inclusive through `windowEnd` exclusive (request time plus one second). `totalTokens`, daily, and model totals all use that window, not lifetime totals. `todayPoints`/`todayTokens` start at UTC midnight. Dates are `YYYY-MM-DD`; nonempty usage fills absent dates with zero, while no usage returns empty daily/model arrays. Points are micro-credits divided by 1,000,000. Ledger input already includes cache creation/read tokens; total tokens are input plus output. Only committed Usage entries count, deduplicated by invocation; pending/held reservations, topups, adjustments, and retry/error traces do not contribute. Provider IDs, target models, costs, USD estimates and reference prices are not exposed by these statistics.

If retained ledger details are incomplete because usage within the window has been archived, `settledUsage` is null and `settledUsageUnavailableReason` explains unavailability. Archived financial summaries cannot reconstruct tokens or per-model usage. Older archives outside the window have no effect. Older gateways without this extension remain supported by CLI with `settledUsage: null`; missing statistics are never fabricated as zero. No frontend/runtime edits or production migration are included.
