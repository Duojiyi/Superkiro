# 客户端热更新发布规范

客户端从我们自己的服务器（`https://kiro.rent/downloads/releases.json`）自更新，不经 GitHub。
每个版本条目由离线私钥签名，客户端只安装签名有效、且版本号严格高于自身的发布；因此即便
下载服务器被攻破，也无法向客户端推送伪造更新或强制降级。

## 一、密钥

- 生产私钥：`deploy/update_signing.py keygen` 生成到 `.acceptance/update-signing-key.pem`（已被
  git 忽略）。**只在离线可信终端持有，绝不上传服务器、不进版本库、不写日志。**
- 公钥编译进客户端 `crates/desktop-host/src/update.rs` 的 `UPDATE_KEYS`。
  `deploy/update_signing.py public` 打印当前公钥。
- **务必离线备份私钥。** 私钥丢失后，已安装的客户端将无法再收到任何更新，只能全部手动替换。
- 建议对私钥文件本身再加密存放（如放入密码库或加密卷），仅在签名时解密。
- 调试构建（非发布）额外信任一把固定测试钥（种子为字节 42，由本地联调脚本按种子推导，不入库），
  仅调试可信；发布版永不信任它，用它签的清单无法更新任何真实客户端。

### 轮换密钥（先加后换，避免断更）

1. 用 `keygen` 生成新私钥（换一个路径，勿覆盖旧钥）。
2. 把新公钥**追加**进 `UPDATE_KEYS`（保留旧公钥），发布一个仍用**旧私钥**签名的新版本。
   等这一版覆盖到全部客户端后，它们就同时信任新旧两把钥。
3. 之后改用新私钥签名发布。确认无回退需求后，再在后续版本里移除旧公钥。

> 注意：发布脚本用 `update.rs` 源码里的 `UPDATE_KEYS` 自检“这把钥客户端是否信任”。它校验的是
> 下一次构建的客户端所信任的钥，不是**线上已安装**客户端所信任的钥。轮换必须按上面的顺序，
> 否则线上旧客户端会静默收不到更新。

## 二、构建

发布版必须带版本号（客户端据此判断自身版本并比较线上发布）：

```sh
python scripts/build_desktop.py --release-version 2026.09.25      # Windows 单文件
# CI：Desktop Native Packages 工作流，手动触发时填 release_version
```

版本号为一到四段数字（如 `2026.09.25`、`2026.09.25.1`），按数值逐段比较。构建会把
`superkiro-release:<版本>;` 标记嵌入二进制；发布脚本据此拒绝“构建版本与发布版本不符”的产物，
避免客户端每次启动都重装同一发布。不带 `--release-version` 的构建不自更新（供本地开发）。

## 三、验收后发布

产物先经既有验收（`--acceptance` 收据核对精确字节），再签名发布：

```sh
python .acceptance/ssh_secret.py | python deploy/publish_native_windows.py \
  --version 2026.09.25 --source dist/Superkiro.exe --acceptance <收据.json>
# macOS：publish_native_macos.py，另加 --arch arm64|x64
```

- 默认发布为**强制更新**（`mandatory: true`）。加 `--optional` 则客户端可暂缓。
- 发布前务必先在两个方向实测新构建可正常启动并确认：N-1 → N、N → N+1。强制更新一旦推出，
  一个无法启动的版本会让所有客户端走回滚（见下）。谨慎起见可先 `--optional` 灰度，再转强制。

## 四、客户端如何保证不被“更新砖化”

- 核心原则：**新版本确认之前，用户双击启动的那个客户端文件一个字节都不动。**
- 安装：下载（断点续传）并校验签名与哈希后，新版本暂存在客户端旁边的隐藏文件夹里
  （`.<客户端文件名>.<版本>.new`，里面的文件名与客户端相同），从那里以“试运行”启动，
  旧版本退出。下载完成进入“校验并安装”后不再提供“暂停”按钮；在那之前点暂停，什么都不会
  启动，已下载的内容保留，下次不必重下。
- 试运行最多等 120 秒报到。安全软件（360、火绒等）弹窗询问、扫描新文件造成的等待超时，
  **不计为失败**；只有试运行自己退出或崩溃才计一次。
- 确认：试运行的新版本把带本机状态的页面**真正渲染出来之后**才确认（纯本地，不依赖网络或
  更新服务器；首次读取状态失败会自动重试几次）。确认时它把自己换到原位置：Windows 一步改名
  覆盖，macOS 一步互换两个 .app，任何时刻原位置都有一个能用的客户端；只有旧文件正被占用时
  才退回“先移开、再换入、失败则移回（移不回就复制回）”的两步。
- 新版本**没能确认**（崩溃、界面没起来、被杀软隔离）：原位置仍是旧版本，用户照常能用；
  下次启动会把这次试运行记为一次失败。同一份字节失败两次即拒绝 7 天（机器原因造成的失败
  不会永久挡住这个版本；时钟跑快了也不会让拒绝变长）。
- 试运行 3 分钟内界面**一个请求都没发出**，才会主动让位给旧版本；界面一旦发出过请求就不再
  让位，客户正在做的任何操作都不会被打断。让位时只有旧版本真的启动了才退出。
- 试运行期间用户再双击，新启动的进程最多等 30 秒让它就位，然后交给正在运行的实例，不会把
  活着的试运行误判为失败。
- 删除暂存文件夹前会核对它确实是客户端旁边、按上述规则命名的那个隐藏文件夹，别的路径一概
  不删。更新状态文件暂时读不了（被扫描占用）时，什么都不判定、不覆盖。
- 强制更新在非重启阶段随时可以“暂时进入客户端”（下载中会暂停，下次从断点继续），并始终能
  “还原 Kiro 配置”，不会被锁死。
- 界面渲染出错时显示错误页：可重新加载、从官网下载、退出，窗口可拖动、最小化、收起；
  **错误页里自动更新照常工作**，所以一个界面坏掉的版本也能被下一版修好。
- 若某强制版本在客户端持续启动失败被拒，线上应把版本号上抬、修复后重新发布（新哈希不在拒绝
  名单，可正常安装）。

### 版本之间的约定（从本版起固定，以后的版本必须兼容）

新旧两个版本在一次更新里各做一半，所以下面这些一旦发布就不能再改：

- 环境变量：`SUPERKIRO_UPDATE_HANDOFF`（安装者的进程号）、`SUPERKIRO_UPDATE_MARKER`
  （试运行报到用的标记文件路径，试运行创建即算报到）、`SUPERKIRO_UPDATE_FALLBACK`
  （让位时传给旧版本的试运行进程号）。
- 状态目录：`%LOCALAPPDATA%\app.superkiro.desktop\`（macOS 为
  `~/Library/Application Support/app.superkiro.desktop/`），与 Tauri 的 `app_local_data_dir` 相同。
- 锁（操作系统文件锁，进程结束自动释放）：`update.lock` 由安装者持有到退出，试运行在安装者
  退出后也持有到确认；`update-trial.lock` 由试运行从启动第一刻持有到确认。判定、清理都要求
  两把锁同时空闲。
- 状态文件 `update-state.json`：`pending` = `{version, sha256, staged, executable, current,
  current_executable}`；`failures` = `{哈希: 次数}`；`rejected` = `{哈希: 拒绝时的 Unix 秒}`。
